## 目标

1. **第一版**：实现占位 Pod 机制，然后成功发放 microVM。
2. **保留身份（identity）和可观测（observability）的可扩展性。** 第一版不交付这两条线的功能，但以后加功能时不返工。
3. **实现上可以复用 sandbox-pool**，但复用不是要求，按实际需要取舍。必要的组件在 agentcube 仓库里维护。
4. **后续版本**由本计划安排，最终用于向上游社区提出 roadmap。

## 对目标的理解

标了“假设”的是计划作者的读法，需要负责人确认，对应“待决定事项”里的编号。

1. **第一版的两句话。**
   - “实现占位 Pod 机制”读作：池类与池两个对象、池控制器、占位 Pod、`placeholder-agent` 把容量交给节点上的运行时、占位 Pod 丢失后停止准入并重建。
   - “成功发放 microVM”读作（假设，D3）：一次经 AgentCube 原生创建接口的请求，经 WorkloadManager 的 `pool` 后端、沙箱调度器、节点适配器到达运行时；microVM 进入运行状态，会话记录为就绪；能在里面执行一条命令；删除之后池的已承诺量归零。执行命令这一步用运行时自带的数据入口来验证。经 Router 访问沙箱的数据面和 E2B SDK 不在第一版。
2. **身份与可观测。** 数据模型、接口签名和调用路径按清单留好接缝。清单见 [seams.md](seams.md)，分配见“身份与可观测的接缝”一节。
3. **复用 sandbox-pool。** 它只覆盖占位 Pod 这一半，没有任何创建沙箱的代码，并且是四周写成的原型。所以按组件取舍：代码与第一版的需要吻合的就移植，不吻合的新写，见下一节。AgentCube 需要的组件都在 agentcube 仓库里维护，agentcube 不依赖 sandbox-pool 这个模块。
4. **先提案后实现。** 本轮只产出 gap 分析、计划和子任务。每个子任务开工后先写实施提案，批准之后再改代码。

## sandbox-pool 的复用：按组件取舍

sandbox-pool 的作者与本计划的负责人同属一个组织，源码允许复用。但“移植并改造”不是要求，要按实际需要分析。

所以复用是一项许可，不是默认做法。下表按组件判断：第一版需要什么，sandbox-pool 里对应的代码与这个需要吻合到什么程度。判断依据是对 `sandbox-pool/` @ `e440730b` 的函数级盘点，依据和行数在 [gap-analysis.md](gap-analysis.md) 第 3.2 节。

| 组件 | 第一版需要的 | sandbox-pool 里的代码 | 取舍 |
|---|---|---|---|
| 池类控制器 | 按节点选择器展开，一节点一池，名字确定，节点冲突检查 | 历史提交 `b5fb66c` 的 `class_reconciler.go`，做的正是这件事，没有发现与提案相反的假设 | **移植，小改** |
| 池控制器 | Phase 聚合、按 Lease 判活、节点不存在的处理、finalizer；承载体丢失后的重建 | `pool_reconciler.go`，约三分之二的函数对得上；承载体丢失的处理没有；回填节点名、按副本清理的部分用不上 | **移植对得上的部分，承载体一段新写** |
| 占位 Pod 的构造 | 节俭规格 | `pod_builder.go`，逐个字段几乎都与提案相反 | **新写**，约百行 |
| 两个 CRD 的类型 | 提案的对象模型，并要过上游的 API 评审 | 池的类型里一半是 node-ctl、副本集、改容量的字段；池类的类型只在历史提交里 | **新写**，字段形状作参考 |
| shim 的启动握手 | containerd v2 的启动协议 | `shim_proxy.go` 里的 `shimManager`，完整，并且记着提案没有取证的细节 | **原样移植**，这是最有价值的一段 |
| shim 的任务状态机 | 自己应答 Task API | `daemon_ttrpc.go` 里的合成任务状态机可用；`Create` 的大半是改容量的逻辑；四个应答与提案相反 | **状态机移植后改，`Create` 等五个应答重写** |
| `placeholder-agent` 的主体 | 按节点名选池、监听 Pod、分配闸门、调容量接口 | 中心结构体约 70 个字段，其中约 20 个是 node-ctl 的；用动态客户端加标签选池；主函数里大半是密钥材料 | **新写**，只取几个小片段：Lease 续租、condition 的比较与设置、进程锁、原子写文件 |
| kuasar 的线协议客户端 | 读池状态、排空 | `pkg/nodectl` 的客户端与编解码，与 kuasar 当前版本一致 | **移植**；000-5 先评估能否直接依赖 kuasar 自己的协议包 |
| 指标、两个 `main`、小工具函数 | 按 agentcube 的约定和提案的指标规则 | 指标前缀与埋点方式不同；工具函数有一个与 apimachinery 的现成函数重复 | **新写**，指标清单作参考 |
| 测试 | — | 全部建在它自写的内存客户端上 | **重写**；它的用例场景作参考 |
| 节点适配器、容量接口、节点管理接口、会话路径 | — | 没有 | **新写** |

合起来，sandbox-pool 里对第一版有实际复用价值的代码约 2400 行（非测试），集中在池类控制器、池控制器、shim 三处。这是计划作者按函数清单估的，不是做出来之后量的。它比参考实现分析报告里“约 500 行原样、约 6000 行改造”的口径小，差别主要在 `placeholder-agent`：报告把它的四个大文件算作“改造后移植”，逐函数看下来，要留的骨架建在动态客户端和标签选择上，而提案要的是按节点名选池，改造不如新写。

另外两条约定：

- 必要的组件（池控制器、shim、`placeholder-agent`、节点适配器）都在 agentcube 仓库里维护，agentcube 不依赖 sandbox-pool 这个模块。
- 凡是移植的文件或片段，出处记在子任务的实施提案里，并注明是原样取用还是改过。

## 开发计划

### 版本总览

| 版本 | 目标 | 对应提案 | 准出 |
|---|---|---|---|
| 第一版 | 占位 Pod 机制；经原生创建接口发放 microVM；留好身份与可观测的接缝 | 阶段一的一个子集 | 本文“第一版的准出标准” |
| 第二版 | 数据面与 E2B 核心档：未修改的 E2B SDK 创建沙箱并执行命令；绑定到沙箱的访问令牌 | 阶段一，其中含提案的第一个里程碑 | 提案准出标准 一-1、一-10 |
| 第三版 | 阶段一收尾：对账与围栏、多副本放置、运行时一致性测试、可观测补齐、池的运维加固 | 阶段一的其余部分 | 一-2 至 一-13（一-14 是条件项） |
| 第四版 | 运行中调节容量、暂停与恢复、出站与凭据、审计、计量 | 阶段二 | 提案 二-1 起 |
| 第五版 | 负载层、会话组与 fork、委托授权、持久卷、沙箱内观测、GUI 档 | 阶段三 | 提案 三-1 起 |
| 第六版 | 抢占落为暂停、与 NodeShard 并用、第二种运行时 | 阶段四 | 提案 四-1 起 |

提案的阶段一被拆成三版，原因是这里要的第一版比阶段一窄。第一版和第二版面向受控的环境：单个或少量可信的节点，不对多租户开放（D16）。第三版里的两项加固，即按节点身份限制状态写入和适配器重启后的恢复，要在向多节点或多租户环境开放之前完成。

### 第一版的准出标准

| 编号 | 标准 | 对应提案 | 验证环境 |
|---|---|---|---|
| V1-1 | 建一个池类之后，每个被选中的节点上有一个池和一个占位 Pod（档 0，普通 pause Pod），Pod 为 Ready；节点已请求量的增加值等于它的 requests；占位 Pod 不用 `hostNetwork`，池命名空间不需要特权级，租户在其中没有建 Pod 的权限 | 一-3 的档 0 部分、一-5 | 开发机上的 Kind |
| V1-2 | 占位 Pod 还在 Pending 时池不开放准入；kubelet 分配之后才向节点栈应用容量，并以回读值为准。删除占位 Pod：池立即停止准入并标为 Degraded，已有沙箱存活；控制器在原节点重建，过了分配闸门才恢复准入。删除全部池之后节点可分配量回到启用之前 | 一-4 | 开发机上的 Kind（假运行时）；带 KVM 的机器（真运行时） |
| V1-3 | 档 1（空操作 shim）：占位 Pod 为 Ready，节点上只有一个 shim 进程，没有容器进程、rootfs 挂载和容器 cgroup；重启 containerd 后任务保留；`Update` 应答成功。**不在关键路径上**：实验不通过时第一版以档 0 准出，并记录原因 | 一-3 的档 1 部分 | 开发机上的 Kind |
| V1-4 | 经原生创建接口发起一次创建，模板选择 `pool` 后端：microVM 进入运行状态，它的进程在池所在的 Kubernetes 节点上（记录进程与 cgroup 的路径、资源配置）；会话记录为就绪，带后端、池、节点；能在其中执行一条命令；删除后运行时里没有这个沙箱，池的已承诺量归零。创建与删除期间没有按会话的 Kubernetes API 写入，也没有新增 Kubernetes 对象。执行命令的做法：节点上的工具用运行时的凭据申请一次性的执行令牌，经运行时的数据入口执行 | 一-2 的一部分 | 带 KVM 的机器 |
| V1-5 | 池放不下时，创建在有限时间内向客户端返回“无容量”；拒绝由运行时做出，适配器只翻译；已有的沙箱不被销毁，也不被暂停。判据、耗时上限和已有沙箱的行为由 000-5 的实验确定。实验表明无法可靠识别时，降低这条标准要先经负责人批准，不以“启动失败”视为通过 | 一-7 的第 5 条、一-8 的一小部分 | 带 KVM 的机器；开发机上的 Kind（假运行时） |
| V1-6 | 现有原生接口的端到端测试在 `pod` 后端上不改即通过；创建池会话由开关控制，默认关闭，关闭时不产生新的池会话，已有的池会话仍能被删除和回收 | 一-12 的前半 | 开发机上的 Kind |
| V1-7 | 接缝清单里分给第一版的条目逐条有检查记录。其中可运行验证的：一次创建是从入口到节点适配器的一条 trace，含等待就绪；每次状态变化有一条生命周期事件；指标标签里没有随会话数增长的标识；没有登记的操作被拒绝并留下带主体和原因的日志 | 一-10、一-11 的一部分 | 开发机上的 Kind；带 KVM 的机器 |

第一版明确不包含：经 Router 的数据面和 E2B；访问令牌的签发与校验；出站网络；运行中改池的大小；暂停与恢复；多副本并发放置；完整的库存对账；节点压力下的驱逐次序实验（提案最重的一条风险，第一版只如实写明没有验证）。

### 验证环境

| 层 | 验什么 | 在哪 |
|---|---|---|
| 静态与单元 | 生成代码、lint、单测；适配器生成的运行时配置的静态校验 | 开发机 |
| Kubernetes 一侧 | CRD、池控制器、占位 Pod 两档、分配闸门、容量交接（假运行时）、后端重构的回归、`pool` 后端对假运行时的端到端 | 开发机上的 Kind（kind v0.33.0，默认节点 Kubernetes v1.37.0、containerd 2.x） |
| 运行时单机 | 000-5 的实验；适配器对真运行时的调用 | 带 KVM 的机器 |
| 端到端 | 从池到“创建、执行、删除”；节点栈与 Kubernetes 节点共存 | 带 KVM 的机器上的 Kind 或单节点集群 |

开发机没有 `/dev/kvm`，CPU 没有虚拟化标志，kuasar-sandbox 没有不依赖硬件虚拟化的路径，所以 microVM 在开发机起不来。带 KVM 的机器的要求：x86_64 或 arm64 的 Linux；`/dev/kvm` 可读写（裸金属，或开了嵌套虚拟化的虚拟机）；宿主页大小是 4 KiB；cgroup v2；内核不低于 5.10；rootful 的 Docker 或 Podman；至少 4 个 CPU、12 GiB 内存。

V1-4 的正式证据要求 microVM 的进程确实在池所在的 Kubernetes 节点上。把运行时的系统容器与 Kind 节点并列放在同一台宿主机上，只能证明逻辑链路，不能当作 V1-4 的证据。

用 CubeSandbox 加 PVM 在开发机验证是可能的，但要给开发机换内核并重启，本计划不采用，理由见 [gap-analysis.md](gap-analysis.md) 第 4.2 节。它作为对冲实验留在 000-5 里，只在另一台可丢弃的虚拟机上做，并且要先得到负责人的同意。

|---|---|---|
| 1 | 拿不到带 KVM 的机器，里程碑 B、C 无法验证 | 里程碑 A 不受影响；对冲是在可丢弃的虚拟机上试 PVM（000-5），它通过也只说明这类机器能跑 microVM |
| 2 | kuasar 的容量拒绝是异步的：先返回已受理，之后沙箱变为 dead，没有机读的原因；默认超分时还可能是别的沙箱被暂停 | 000-5 是运行时接入的硬闸门：给出拒绝的判据、耗时上限和已有沙箱的行为。第一版关闭超分（D15）。仍然无法可靠识别时有三条出路，都要负责人批准：降低 V1-5、请上游补接口、更换运行时 |
| 3 | 节点栈与 Kubernetes 节点怎样共存没有定：上游的系统容器镜像不能原样作 Pod，本地控制 socket 在容器内部 | 000-5 的共存实验；结果决定节点适配器的打包 |
| 4 | 后端接口的重构落在上游改动最频繁的文件上，现有单测按函数名打桩 | 000-8 先改测试再改代码；尽早做，缩短与上游分叉的时间 |
| 5 | sandbox-pool 是原型：没有端到端验证，文档与代码多处不一致，代码里带着三个与提案相反的假设。移植时容易把这些一起带进来 | 只移植与需要吻合的部分；每个子任务列出“取什么、不带什么”；以源码为准，不以它的文档为准；移植来的行为同样要过子任务的验收 |
| 6 | 占位 Pod 的 requests 只是记账，内核不据此限制沙箱；节点栈的账本守不住时，节点压力下被驱逐的是常规 Pod | 第一版不验证，在说明里写明；第三版做节点压力实验 |
| 7 | kuasar 上游变化快，sandbox-pool 依赖的行为在当前版本上已经有三处不成立 | 适配器钉住一个 kuasar 版本，以源码和实验为准，不以 sandbox-pool 的文档为准 |
| 8 | 提案的接口都是示意，有七条未决问题直接卡住第一版 | 000-1 集中定稿；清单见 [gap-analysis.md](gap-analysis.md) 第 3.4 节 |
| 9 | 回滚到旧版本，或误启动一个旧的 WorkloadManager 副本：旧的垃圾回收会删掉池会话的记录而不销毁 microVM。开关只管新建，管不了存量 | “允许创建”与“处理存量”分开：关掉创建开关之后仍然能删除和回收池会话。回滚之前先停止创建并清空池会话。做新旧版本交叉的测试。更强的办法是让池会话不进旧垃圾回收读的那两个索引，在 000-7 里评估 |
| 10 | 运行时凭据、证书、适配器地址、网络路径这条引导链路第一版靠手工安装 | “第一版的引导与连接”一节逐项指定了提供方和验收；000-11 的安装说明要让另一个人照做能走通 |
| 11 | WorkloadManager 在节点已经受理创建之后崩溃，留下没有记录指向的 microVM | 000-10 在每次向节点提交之前先把目标节点、池、标识写进记录；失败与重启的用例进验收 |

## 不在范围内

- 提案的非目标：新的 VMM、SDK 或 agent 框架；替换默认调度器；节点自动扩缩；PodGroup 与 Queue 准入；Volcano 以外的调度器。
- 修改内部的设计提案。
- 给开发机换内核或安装运行时。
- 推送到 `upstream`，以及创建或发布 GitHub issue、PR、评论。
