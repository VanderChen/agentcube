## 目标

1. **第一版**：把占位 Pod 的流程走通，包括占位 Pod 的原地调整（resize）；然后经 containerd 加 Kata 成功发放 microVM。第一阶段放弃快照管理这一类事情。
2. **保留身份（identity）和可观测（observability）的可扩展性。** 第一版不交付这两条线的功能，但以后加功能时不返工。
3. **实现上可以复用 sandbox-pool**，但复用不是要求，按实际需要取舍。必要的组件在 agentcube 仓库里维护。
4. **后续版本**由本计划安排，最终用于向上游社区提出 roadmap。

## 对目标的理解

标了“假设”的是计划作者的读法，需要负责人确认，对应“待决定事项”里的编号。

1. **第一版的范围。**
   - “占位 Pod 的流程”读作：池类与池两个对象、池控制器、占位 Pod、`placeholder-agent` 把容量交给节点、占位 Pod 丢失后停止准入并重建，以及手工改池的大小时占位 Pod 的原地调整。占位 Pod 还是一个，它占住的资源用来在节点上起多个 Kata 沙箱。
   - “成功发放 microVM”读作（假设，D3）：一次经 AgentCube 原生创建接口的请求，经 WorkloadManager 的 `pool` 后端、沙箱调度器、节点适配器到达节点；containerd 经 Kata 拉起一台 microVM，会话记录为就绪；能在里面执行一条命令；删除之后池的已承诺量归零。执行命令这一步经 containerd 验证。经 Router 访问沙箱的数据面和 E2B SDK 不在第一版。
2. **身份与可观测。** 数据模型、接口签名和调用路径按清单留好接缝。清单见 [seams.md](seams.md)，分配见“身份与可观测的接缝”一节。
3. **复用 sandbox-pool。** 它只覆盖占位 Pod 这一半，没有任何创建沙箱的代码，并且是四周写成的原型。所以按组件取舍：代码与第一版的需要吻合的就移植，不吻合的新写，见下一节。AgentCube 需要的组件都在 agentcube 仓库里维护，agentcube 不依赖 sandbox-pool 这个模块。
4. **先提案后实现。** 本轮只产出 gap 分析、计划和子任务。每个子任务开工后先写实施提案，批准之后再改代码。
5. **一个节点只有一种沙箱运行时（2026-11-25 确认，D21）。** PVM 的实验测到 Kata 和 CubeSandbox 各要各的宿主之后定的：不需要两者并存；一个节点上只装一种发放沙箱的运行时，以后接入带快照的运行时，放在另外的节点上。这里的“运行时”指发放沙箱的那一种（Kata、kuasar-sandbox、CubeSandbox）；Kubernetes 自己用的 runc 和档 1 的占位 shim 不算（假设）。后续的开发和 000-5 第二段的实验在那台虚拟机上做，用 Kata 的那一种宿主（假设，D2）。

## sandbox-pool 的复用：按组件取舍

sandbox-pool 的作者与本计划的负责人同属一个组织，源码允许复用。但“移植并改造”不是要求，要按实际需要分析。

所以复用是一项许可，不是默认做法。下表按组件判断：第一版需要什么，sandbox-pool 里对应的代码与这个需要吻合到什么程度。判断依据是对 `sandbox-pool/` @ `e440730b` 的函数级盘点，依据和行数在 [gap-analysis.md](gap-analysis.md) 第 3.2 节。

| 组件 | 第一版需要的 | sandbox-pool 里的代码 | 取舍 |
|---|---|---|---|
| 池类控制器 | 按节点选择器展开，一节点一池，名字确定，节点冲突检查 | 历史提交 `b5fb66c` 的 `class_reconciler.go`，做的正是这件事，没有发现与提案相反的假设 | **移植，小改** |
| 池控制器 | Phase 聚合、按 Lease 判活、节点不存在的处理、finalizer；承载体丢失后的重建 | `pool_reconciler.go`，约三分之二的函数对得上；承载体丢失的处理没有；回填节点名、按副本清理的部分用不上 | **移植对得上的部分，承载体一段新写** |
| 占位 Pod 的构造 | 节俭规格 | `pod_builder.go`，逐个字段几乎都与提案相反 | **新写**，约百行 |
| 两个 CRD 的类型 | 提案的对象模型，并要过上游的 API 评审 | 池的类型里一半是 node-ctl、副本集、改容量的字段；池类的类型只在历史提交里 | **新写**，字段形状作参考 |
| shim 的启动握手 | containerd v2 的启动协议 | `shim_proxy.go` 里的 `shimManager`，完整，并且记着提案没有取证的细节 | **原样移植**，这是最有价值的一段 |
| shim 的任务状态机 | 自己应答 Task API | `daemon_ttrpc.go` 里的合成任务状态机可用；`Create` 的大半是改容量的逻辑；四个应答与提案相反 | **状态机移植后改，`Create` 等五个应答重写** |
| `placeholder-agent` 的主体 | 按节点名选池、监听 Pod、分配闸门、调容量接口 | 中心结构体约 70 个字段，其中约 20 个是 node-ctl 的；用动态客户端加标签选池；主函数里大半是密钥材料 | **新写**，只取几个小片段：Lease 续租、condition 的比较与设置、进程锁、原子写文件 |
| 占位 Pod 的原地调整 | 写 `/resize`、等 kubelet 分配、扩缩的次序与回退 | `pool_resize.go`、`pod_spec_updater.go` 和 `daemon_ttrpc.go` 里的扩缩处理，约 1300 行。它用普通的 Pod patch 并指望容器被重建，在标准 Kubernetes 上走不通 | **重写**；“先查已承诺量再缩”和“被推迟的缩容从状态里恢复”两个做法作参考 |
| kuasar 的线协议客户端 | 第一版用不上：运行时取 Kata | `pkg/nodectl` 的客户端与编解码，与 kuasar 当前版本一致 | **不取用**；以后接入 kuasar 时再看 |
| 指标、两个 `main`、小工具函数 | 按 agentcube 的约定和提案的指标规则 | 指标前缀与埋点方式不同；工具函数有一个与 apimachinery 的现成函数重复 | **新写**，指标清单作参考 |
| 测试 | — | 全部建在它自写的内存客户端上 | **重写**；它的用例场景作参考 |
| 节点适配器、容量接口、节点管理接口、会话路径 | — | 没有 | **新写** |

合起来，sandbox-pool 里对第一版有实际复用价值的代码约 2000 行（非测试），集中在池类控制器、池控制器、shim 三处。这是计划作者按函数清单估的，不是做出来之后量的。它比参考实现分析报告里“约 500 行原样、约 6000 行改造”的口径小，差别主要在 `placeholder-agent`：报告把它的四个大文件算作“改造后移植”，逐函数看下来，要留的骨架建在动态客户端和标签选择上，而提案要的是按节点名选池，改造不如新写。

另外两条约定：

- 必要的组件（池控制器、shim、`placeholder-agent`、节点适配器）都在 agentcube 仓库里维护，agentcube 不依赖 sandbox-pool 这个模块。
- 凡是移植的文件或片段，出处记在子任务的实施提案里，并注明是原样取用还是改过。

## 方向更新（2026-11-24）：先走通占位 Pod 的流程，含 resize；运行时取 Kata

计划的第一稿把首个运行时建议为 kuasar-sandbox，池的大小在第一版固定，运行中调整排在第四版。负责人随后确定了下面的方向，计划据此改过。

**确定的方向。** 第一阶段放弃快照管理这一类事情，先把占位 Pod 的流程走通，包括占位 Pod 的 resize。占位 Pod 还是一个，它占住的资源用来在节点上起多个 Kata 沙箱：containerd 经 Kata 拉起 microVM。

| 事项 | 第一稿 | 现在 |
|---|---|---|
| 首个运行时（D1） | 建议 kuasar-sandbox | containerd 加 Kata，VMM 由实验定（Firecracker、Cloud Hypervisor、Dragonball） |
| 池的大小 | 第一版固定，运行中调整在第四版 | 第一版就做手工调整（D17）；自动调节仍在第四版 |
| 池的账本与准入 | 归运行时，节点适配器只翻译 | 归节点适配器。Kata 不做节点级的记账 |
| 快照、暂停恢复、流量唤醒、模板快速启动 | 第四版，由 kuasar 提供 | 第一阶段放弃。以后靠接入第二种运行时，或者等 Kata 上游 |
| 子任务 | 000-1 至 000-11 | 000-5 改为 Kata 的接入实验；000-6 的驱动改为 containerd 加 Kata；新增 000-12“占位 Pod 的原地调整” |

**为什么这个取舍成立。**

- resize 在两条路线上的难度相反。kuasar 上改容量是一次 conductor 重启，在途的创建会失败；账本归我们自己之后，改容量就是改账本上的数字，再改一个父 cgroup 的上限。
- Kata 的短处是只有创建和删除，没有暂停恢复、快照和模板快速启动。这些正好不在第一阶段的范围里。
- 节点适配器调的是 containerd 的接口，用哪个运行时只是一个名字。开发机上可以先用 runc 当替身把同一条路径走通，不需要 KVM。
- Kata 的沙箱就是 OCI 镜像，与 agentcube 现有的镜像模板对得上，不需要模板构建管线。

**代价。**

- 以后要快照、暂停恢复时，得接入第二种运行时。节点适配器的接口保持与运行时无关，是这个代价有界的前提。
- 账本、准入、每个沙箱的开销、沙箱的网络，Kata 都不提供，要节点适配器自己做。
- 每次创建都是冷启动。
- Kata 要 `/dev/kvm`，开发机上起不了 Kata 的 microVM。

依据是 内部的 Kata 研究笔记和 [gap-analysis.md](gap-analysis.md) 第 3.3、4.2 节。笔记读的是 Kata 4.4.0（commit `2e1efbe1`），是静态阅读。

## 开发计划

### 版本总览

| 版本 | 目标 | 对应提案 | 准出 |
|---|---|---|---|
| 第一版 | 占位 Pod 的完整流程，含手工的原地调整；经 containerd 加 Kata 发放 microVM；留好身份与可观测的接缝。不做快照和暂停恢复 | 阶段一的一个子集，加上阶段二里占位 Pod 热扩容的手工部分 | 本文“第一版的准出标准” |
| 第二版 | 数据面与 E2B 核心档：未修改的 E2B SDK 创建沙箱并执行命令；绑定到沙箱的访问令牌 | 阶段一，其中含提案的第一个里程碑 | 提案准出标准 一-1、一-10 |
| 第三版 | 阶段一收尾：对账与围栏、多副本放置、运行时一致性测试、可观测补齐、池的运维加固 | 阶段一的其余部分 | 一-2 至 一-13（一-14 是条件项） |
| 第四版 | 自动调节容量与向常规负载让出；出站与凭据、审计、计量；接入一种带快照的运行时之后做暂停与恢复 | 阶段二 | 提案 二-1 起 |
| 第五版 | 负载层、会话组与 fork、委托授权、持久卷、沙箱内观测、GUI 档 | 阶段三 | 提案 三-1 起 |
| 第六版 | 抢占落为暂停、与 NodeShard 并用 | 阶段四 | 提案 四-1 起 |

提案的阶段一被拆成三版，原因是这里要的第一版比阶段一窄。第一版和第二版面向受控的环境：单个或少量可信的节点，不对多租户开放（D16）。第三版里的两项加固，即按节点身份限制状态写入和适配器重启后的恢复，要在向多节点或多租户环境开放之前完成。

### 第一版的准出标准

| 编号 | 标准 | 对应提案 | 验证环境 |
|---|---|---|---|
| V1-1 | 建一个池类之后，每个被选中的节点上有一个池和一个占位 Pod（档 0，普通 pause Pod），Pod 为 Ready；节点已请求量的增加值等于它的 requests；占位 Pod 不用 `hostNetwork`，池命名空间不需要特权级，租户在其中没有建 Pod 的权限 | 一-3 的档 0 部分、一-5 | 开发机上的 Kind |
| V1-2 | 占位 Pod 还在 Pending 时池不开放准入；kubelet 分配之后才向节点应用容量，并以回读值为准。删除占位 Pod：池立即停止准入并标为 Degraded，已有沙箱存活；控制器在原节点重建，过了分配闸门才恢复准入。删除全部池之后节点可分配量回到启用之前 | 一-4 | 开发机上的 Kind；带 KVM 的机器 |

### 验证环境

| 层 | 验什么 | 在哪 |
|---|---|---|
| 静态与单元 | 生成代码、lint、单测 | 开发机 |
| Kubernetes 一侧 | CRD、池控制器、占位 Pod 两档、分配闸门、容量交接与原地调整（假运行时）、后端重构的回归 | 开发机上的 Kind（kind v0.33.0，默认节点 Kubernetes v1.37.0、containerd 2.x） |
| 经 containerd 发放（替身） | 节点适配器的账本、准入、池级 cgroup、事件；容量变更；`pool` 后端的端到端。沙箱用 runc 起，不是 microVM | 开发机上的 Kind |
| Kata 的 microVM | 000-5 里需要 KVM 的实验；适配器换成 Kata 之后的发放与 resize；端到端 | 带 KVM 的机器上的 Kind 或单节点集群 |

开发机能做的比第一稿多。节点适配器调的是 containerd 的接口，用哪个运行时只是一个名字，所以开发机可以先用 runc 把发放、准入、容量变更这条路径走通，换成 Kata 时改的是配置。这一点是分析，由 000-5 在开发机的实验确认。

开发机不能做的是让 Kata 真的起一台虚拟机。开发机没有 `/dev/kvm`，CPU 没有虚拟化标志；Kata 要求 `/dev/kvm`，它自己的仓库里没有纯软件模拟的路径。带 KVM 的机器的要求：x86_64 或 arm64 的 Linux；`/dev/kvm` 可读写（裸金属，或开了嵌套虚拟化的虚拟机）；cgroup v2；containerd 2.x；至少 4 个 CPU、12 GiB 内存；选 Firecracker 时还要给 containerd 配 devmapper 快照器。

V1-4 的正式证据要求沙箱确实是 Kata 起的 microVM，并且它的进程在池所在的 Kubernetes 节点上。用 runc 当替身的结果只能证明路径，不能当作 V1-4 的证据。

**像开发机这样没有 KVM 的虚拟机。** 这类机器上要起 microVM，只有 PVM 一条路。PVM 是 KVM 的一个厂商模块，不需要硬件虚拟化，装上之后节点上就有 `/dev/kvm`。2026-11-24 读了 PVM 项目的文档和测试脚本（没有运行），结论是：

- **Kata 在这类机器上有路。** PVM 项目写明它是为了在没有硬件虚拟化的情况下支持 Kata 而做的；它发布宿主模块包时的测试包含 Kata 配 QEMU、Dragonball、Cloud Hypervisor，经 containerd 发起，不经 CRI。条件是宿主装 PVM 的内核模块并重启、guest 内核换成带 PVM 支持的那一个。Firecracker 不在它测过的 Kata 组合里。
- **没有在这类机器上验证过。** 现成的模块包对应的内核版本与开发机不同；PVM 项目说 AMD 的机器要另外取证，开发机是 AMD 的虚拟机。
- **Kata 不行时看 kuasar（负责人 2026-11-24 的要求），但 kuasar 在这类机器上的处境更差。** kuasar-sandbox 的仓库里检索不到 PVM；它自带的 guest 内核是 6.1，PVM 的 guest 支持只有 6.6、6.7、6.12；还要改它的代码去限制 guest 的地址宽度。开源的 Kuasar 同样没有 PVM 的记录。所以先分清是这类机器跑不了 PVM，还是 Kata 的问题，再决定要不要为 kuasar 做移植。

这些实验（E0、E1 和之后的判断次序）在 000-5 里。它们要换内核并重启，本计划不在开发机上做，理由见 [gap-analysis.md](gap-analysis.md) 第 4.2 节；只在另一台可丢弃的虚拟机上做，并且要先得到负责人的同意。2026-11-25 有了这样一台虚拟机，只读的评估记在 000-5 里。同一天负责人批准之后在它上面做了 PVM 的五个实验，结果如下，都是在那一台 AMD 的云主机上测到的，记录在 000-5 里：

- E0，宿主：通过。Ubuntu 的 `6.8.0-139` 内核加 PVM 项目的模块包，有 `/dev/kvm`，Docker 和 Kind 可用。
- E1，Kata：通过。Kata 4.2.0 配 QEMU、Dragonball、Cloud Hypervisor 都起得了沙箱，各十次创建、执行、删除全部成功。创建一个沙箱 6.5 到 8 秒，没有调过。只测了 containerd 这一层，没有经过 Kubernetes。
- E2，CubeSandbox 在同一个宿主上：不通过。它自带的 PVM guest 内核在这个宿主上一启动就复位。
- E3，CubeSandbox 在它自己的 PVM 宿主内核上：通过。从模板建沙箱 79 到 99 毫秒，十次全部成功。
- E4，对照：启动参数相同时，这两个宿主和这两个 guest 内核只有原配的组合起得来，换过来 guest 就复位（用两个 VMM 直接启动 guest 内核测的）。在 CubeSandbox 的宿主内核上，Kata 把 guest 内核换成 CubeSandbox 的之后，Dragonball 和 Cloud Hypervisor 起得了沙箱。

所以在这类机器上，Kata 和 CubeSandbox 都能靠 PVM 运行，各自要配它那一边的宿主和 guest 内核；为什么不能换着配没有查，每边只测了一个版本。Kata 照 PVM 项目的做法，用发行版的内核（要是模块包对应的那个版本，并带 `nokaslr` 启动）加一个模块包；CubeSandbox 测过的可用做法是换成它自己的宿主内核。两者在同一个宿主上并存不是需求：2026-11-25 负责人说明不需要并存，以后同一个节点上也只放一种运行时（D21）。E4 里顺带测到的一种并存的搭法（用 CubeSandbox 的宿主内核，Kata 改用 CubeSandbox 的 guest 内核）只作记录，不再追。后续的开发和第二段的实验用 Kata 的那一种宿主。

**第四版及以后**按提案 `roadmap.md` 的阶段二至四。提案自己指出阶段二最重。

第四版有三个硬前提，留字段解决不了，取证要提前到第二版的时间里做：

- **一种带快照的运行时。** 暂停恢复、快照、流量唤醒、模板快速启动，Kata 都没有。候选是 kuasar-sandbox、CubeSandbox，或者等 Kata 上游的提案合入。它经同一套节点管理接口接入，作为第二种驱动；按 D21，它装在另外的节点上，不与 Kata 装在同一个节点。
- **出站流量怎样归到单个沙箱。** Kata 没有出站策略的机制，要在节点上自己做。沙箱网络取 connector 时，端口由入口设备认定，guest 伪造不了，可以作归属的键；但键会随端口回收而复用，策略和有状态的 NAT 它也不做，出口代理或外部网关仍然要有（D20）。
- **可靠的计量需要不丢的状态转换时间点。** containerd 的事件流够不够用，要取证。

第四版内部的次序：自动调节建在第一版的手工调整之上，租户并发上限和“只给建议”的调节模式先于自动调节；暂停与恢复先于回收，并且都在带快照的运行时接入之后；出站归属的绑定先于凭据注入；可靠的状态转换链路先于计量。

## 风险

| # | 风险 | 应对 |
|---|---|---|
| 1 | 拿不到带 KVM 的机器，Kata 的 microVM 无法验证 | 里程碑 A 和用 runc 当替身的路径不受影响。另一条路是在可丢弃的虚拟机上试 PVM 加 Kata（000-5）：有 PVM 项目一侧的依据；2026-11-25 在一台 AMD 的云主机上测过：PVM 的宿主起得来（E0），Kata 4.2.0 在上面起得了沙箱（E1）。只有一台机器、一款 CPU，只测到 containerd 这一层。它不通过时，kuasar 不是现成的退路：kuasar 没有 PVM 的支持，要重编 guest 内核并改代码 |
| 2 | Kata 只有创建和删除。暂停恢复、快照、模板快速启动、流量唤醒以后都要靠第二种运行时或 Kata 上游 | 这是第一阶段已经接受的取舍。节点适配器的接口保持与运行时无关；没有的能力如实声明为没有；第二种运行时的取证提前到第二版的时间里做 |
| 3 | 账本、准入、每个沙箱的开销、沙箱的网络都要节点适配器自己做。Kata 里 VM 的默认内存是 2048 MiB 且不预分配，记少了会超出池 | 000-5 量每个沙箱的实际开销；账本按声明规格加固定开销；池级的父 cgroup 兜底（D18） |
| 4 | Kata 里各种 VMM 差别大。Firecracker 是功能最少的组合：它的运行时类在已弃用的 Go runtime 上，要自己配 devmapper，内存不能热增减 | VMM 由 000-5 的实验定，比较启动时延、每个沙箱的开销、安装成本和维护状态 |
| 5 | 原地调整被推迟或不可行；Kubernetes 1.38 起调度器对被推迟的调整默认会抢占；缩容时已承诺量高于目标 | 000-12：优先级类不超过 1e9 且不抢占别人；扩容被推迟时超时回退，被判为不可行时直接回退；缩容被推迟时占位 Pod 的 requests 不动。第一版没有容量调节器，卡住的操作靠一个人工入口撤销或重试。提案的实验 KE-P3、KE-S6 在开发机上的 Kind 上先做，1.35 和 1.37 各一遍 |
| 6 | 后端接口的重构落在上游改动最频繁的文件上，现有单测按函数名打桩 | 000-8 先改测试再改代码；尽早做，缩短与上游分叉的时间 |
| 7 | sandbox-pool 是原型：没有端到端验证，文档与代码多处不一致，代码里带着三个与提案相反的假设。移植时容易把这些一起带进来 | 只移植与需要吻合的部分；每个子任务列出“取什么、不带什么”；以源码为准，不以它的文档为准；移植来的行为同样要过子任务的验收 |
| 8 | 占位 Pod 的 requests 只是记账，内核不据此限制沙箱；账本守不住时，节点压力下被驱逐的是常规 Pod | 第一版的应对是池级的父 cgroup（D18）。它守不守得住、节点压力下 kubelet 驱逐谁，第一版不验证，在说明里写明；第三版做节点压力实验 |
| 9 | 提案的接口都是示意，有七条未决问题直接卡住第一版 | 000-1 集中定稿；清单见 [gap-analysis.md](gap-analysis.md) 第 3.4 节 |
| 10 | 回滚到旧版本，或误启动一个旧的 WorkloadManager 副本：旧的垃圾回收会删掉池会话的记录而不销毁 microVM。开关只管新建，管不了存量 | “允许创建”与“处理存量”分开：关掉创建开关之后仍然能删除和回收池会话。回滚之前先停止创建并清空池会话。做新旧版本交叉的测试。更强的办法是让池会话不进旧垃圾回收读的那两个索引，在 000-7 里评估 |
| 11 | Kata 的安装、证书、适配器地址、网络路径这条引导链路第一版靠手工安装 | “第一版的引导与连接”一节逐项指定了提供方和验收；000-11 的安装说明要让另一个人照做能走通 |
| 12 | WorkloadManager 在节点已经受理创建之后崩溃，留下没有记录指向的 microVM | 000-10 在每次向节点提交之前先把目标节点、池、标识写进记录；失败与重启的用例进验收 |
| 13 | 没有模板快照，每次创建都是冷启动 | 第一版只记录启动时延，不设指标。要快速启动时，在 Kata 里换成带模板的 VMM，或者接入第二种运行时 |
| 14 | 承载体长期恢复不了：占位 Pod 的预留没有了，沙箱还在。提案要求限期排空，原先指望节点栈执行，Kata 不会代做 | 第一版不自动做：池保持停止准入并告警，人工排空，步骤写进安装说明（000-3、000-11）。记为已知缺口 |
| 15 | 账本归我们自己之后，记账的时点错了就会超出池：创建失败或收到退出事件时，虚拟机可能还占着资源 | 000-6：预算从准入起占着，直到宿主上的资源确认释放；声明的规格、microVM 的配置、宿主上的预算三个量分开，换算规则由 000-5 实测；每个沙箱有自己的 cgroup 上限 |

## 不在范围内

- 提案的非目标：新的 VMM、SDK 或 agent 框架；替换默认调度器；节点自动扩缩；PodGroup 与 Queue 准入；Volcano 以外的调度器。
- 修改内部的设计提案。
- 给开发机换内核或安装运行时。
- 推送到 `upstream`，以及创建或发布 GitHub issue、PR、评论。
