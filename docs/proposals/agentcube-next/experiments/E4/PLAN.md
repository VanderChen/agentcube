# E4：E2 的失败是不是五级页表造成的（实验计划）

- 机器：同 E0 到 E3。
- 批准：2026-11-25 负责人要求继续验证，直到能回答 Kata 或 CubeSandbox 在这台 AMD 机器的 PVM 上是否可用。E4 是为了把 E2 的结论弄准，属于这个要求之内。
- 为什么做：E1 到 E3 的记录交给子代理复核，它指出 E2 的归因有一个没有控制的变量。E2 的宿主（Ubuntu `6.8.0-139` 加 PVM 项目的模块）只带 `nokaslr` 启动，五级页表开着；E3 的宿主除了换成 CubeSandbox 的内核，还带着它文档要求的一串启动参数，其中有 `no5lvl`，五级页表关着。CubeSandbox 的宿主内核自己是支持五级页表的（`CONFIG_X86_5LEVEL=y`），可见 `no5lvl` 是它有意要求的。所以 E2 里 microVM 一启动就复位，可能不是“它的 guest 内核与 PVM 项目的模块不配套”，而只是“它的 guest 内核不能在开着五级页表的宿主上跑”。两种解释对计划的含义完全不同：前一种要换宿主内核，后一种加一个启动参数就行，而且 Kata 和 CubeSandbox 可以用同一个宿主。
- 要回答的问题，按次序：
  1. 在 Ubuntu `6.8.0-139` 加 PVM 项目的模块、带 `nokaslr no5lvl` 启动的宿主上，上游的 Cloud Hypervisor 和 Firecracker 能不能启动 CubeSandbox 的 `vmlinux-pvm`。
  2. 能的话：CubeSandbox 本身在这个宿主上能不能建模板、从模板建沙箱、执行代码（标准同 E2 的第 2 到 6 条）；Kata 在这个宿主上是否仍然可用。
  3. 不能的话：换成 CubeSandbox 文档要求的整串参数再试一次；仍然不能，就在 CubeSandbox 自己的宿主上跑一次同样的直接启动，作为“这两个 VMM 本来能启动这个 guest 内核”的对照。
- 状态：见 `RECORD.md`。

## 风险与回退

- 与 E0 相同：新的启动参数下起不来，从控制台重启一次回到 `6.8.0-149`。这条退路在 E2 里实际走过。闸门仍在，CubeSandbox 不会自己启动。
- 启动 CubeSandbox 之前先确认防火墙完整（用改过的脚本，`DOCKER-USER` 链不存在时它会报错），再上保险。
- 没有另做安全评审：用的都是评审过的做法，新的只有一个启动参数。
