# E2：这类机器上 CubeSandbox 能否在 PVM 上起沙箱（实验计划）

- 机器：E0、E1 用过的那台可丢弃虚拟机，ssh 名 `cpu`，现在是 PVM 宿主（`6.8.0-139-generic` 加 `nokaslr`，PVM 项目 v0.1 的模块包）。
- 批准：2026-11-25 负责人要求继续验证，直到能回答 Kata 或 CubeSandbox 在这台 AMD 机器的 PVM 上是否可用。E1 已经回答了 Kata 的一半（通过），E2 回答 CubeSandbox 的一半。
- 与 [000-5 的说明](../../subtasks/000-5-kata-runtime-spikes.md) 的关系：那里把 CubeSandbox 放在“E1 不通过时的对照”。E1 通过了，所以 E2 不是为了定位问题，而是直接回答负责人的问题。它也给总体任务里“内置节点栈在这类机器上能不能用”提供第一份证据。
- 通过标准：
  1. 用 `CUBE_PVM_ENABLE=1` 安装成功，服务都在运行，安装器自己的检查通过。
  2. 从镜像创建模板成功（这一步会起一台 microVM 并做快照）。
  3. 从模板创建沙箱成功（这一步是恢复快照），沙箱到达运行状态。
  4. 在沙箱里执行一段代码并取回输出。
  5. 第 3、4 步加删除，重复十次全部成功。
  6. 宿主的内核日志里没有 `BUG:`、`WARNING:`、`Oops`、`general protection`、`Call Trace`。
- 不在 E2 里做：CubeSandbox 自己的宿主内核（见“两条路”）；多节点；性能测量；暂停与恢复只在时间允许时试一次，不算通过标准。
- 状态：见 `RECORD.md`。

## 两条路，先走哪一条

CubeSandbox 的 PVM 部署文档（`docs/guide/pvm-deploy.md` @ `6843e3f9`）要求换上它自己的宿主内核（基于 OpenCloudOS 6.6.117），并带一长串启动参数重启。PVM 项目的做法不同：它在各发行版自带的内核上装树外的模块包，然后在上面测 CubeSandbox 的模板创建和恢复，v0.1 的发布说明称六个目标全部通过。

这台机器现在就是后一种状态。所以先走后一条路：**不换内核，在现在的 PVM 宿主上装 CubeSandbox**。它通过，就回答了问题，而且与 Kata 用的是同一个宿主，结论可以并排看。它不通过，再评估要不要走 CubeSandbox 文档里的路（换它的宿主内核），那一步要另写计划。

钉住的版本：

| 项 | 版本 | 来源 |
|---|---|---|
| CubeSandbox | v0.8.0 的一键安装包 `cube-sandbox-one-click-v0.8.0-amd64.tar.gz` | GitHub 的发布页。校验和在下载时记下 |
| guest 内核 | 安装包里自带的 `vmlinux-pvm`，由 `CUBE_PVM_ENABLE=1` 选中 | 安装包 |
| 宿主 | 与 E1 相同 | E0 |
| PVM 项目的测试脚本 | `scripts/cubesandbox-pvm-test.sh` @ `276edd0c` | E1 已取到虚拟机上 |
| E2B 的 Python SDK | `e2b-code-interpreter`，版本在安装时记下 | PyPI，用 uv 装在独立的环境里 |

v0.8.0 包含 2026-11-12 合入的“容忍被拒绝的 MSR”（#2254）。E0 测到这台宿主会拒绝写回 MSR 0x3a，所以这个修复在这里应当被用到。

## 只读检查已经知道的三件事

`00-preflight` 的结果（`log-00-preflight.txt`）：

1. `/data/cubelet` 必须在 XFS 上，这台机器只有一块 ext4 的盘。做法：一个稀疏文件里建 XFS，经 loop 设备挂上去。不写进 fstab。
2. 安装器默认用的四个基础镜像（CoreDNS、MySQL、Redis、OpenResty）在 `cube-sandbox-image.tencentcloudcr.com` 上，从这台机器连不上（40 秒超时）；`cube-sandbox-int.tencentcloudcr.com` 连得上。做法：先试原地址；不行就从 Docker Hub 拉同名同版本的官方镜像，再打上安装器要的名字。CubeSandbox 的离线部署文档说安装器会直接用本地已有的镜像。**这是与文档做法的一处偏离**：这四个镜像的内容来自 Docker Hub，不是腾讯的仓库，两者是否逐字节相同没有核对。
3. Docker 没有 compose 插件，安装器会自己用 apt 装 `docker-compose`。

## 安全上的两件事

**一、失联。** CubeSandbox 的服务是开机自启的，它们会在上联网卡上挂 eBPF 程序、改宿主的 DNS 解析；它用 Docker 起的几个容器带着自动重启的策略。如果这些动作切断了 ssh，就没有人能登录去撤销；普通的重启会把同样的服务再启动一次。所以 E0 留下的“重启一次就恢复”的退路在这里不够，要补三样：

1. **开机闸门（`01a-guard.sh`）。** 在安装之前，给 CubeSandbox 的全部单元（按名字前缀 `cube-sandbox-`）和 Docker 的服务、套接字各加一个 systemd 的 drop-in：只有 `/run/e2-allow` 存在才启动。`/run` 是内存文件系统，每次启动之后这个文件都不在。所以不管是保险触发的重启、内核挂死之后的断电重启，还是谁手工重启，起来之后 CubeSandbox 和 Docker 都不会自己启动，机器是安静的、连得上的。要用的时候 `touch /run/e2-allow` 再启动。
2. **把退路实际走一遍（`01b` 到 `01d`）。** 默认启动项原先靠“第 0 项是 `6.8.0-149`”，现在按菜单项的 ID 固定到它。然后做一次普通的重启，确认起来的是 `6.8.0-149`、闸门生效（Docker 没有自己启动）；再用一次性启动项回到 PVM 宿主。E0 的复核指出这条退路自 E0 以来只是从配置读出来的，没有走过；这里补上。
3. **定时的保险（`01-deadman.sh`）。** 管的是“机器还在运行、但 ssh 断了”这一种情况。一个定时器，到时间没有被续上或取消就重启（先正常重启，180 秒没有完成就强制）。续期的做法是先上一个新的、确认它在、再撤旧的，中间没有空窗。从上防火墙之前开始，一直到收尾，始终有一个在。每次续期都是从开发机新开的 ssh 连接做的，能续上本身就说明 ssh 还通。

收尾（`12-quiesce.sh`）也用重启：停掉 CubeSandbox，去掉它那几个容器的自动重启策略，然后用一次性启动项重启回 PVM 宿主。重启之后 eBPF 程序、DNS 的改动、防火墙规则都不在了，闸门保证 CubeSandbox 不会自己起来。之后才把 Docker 的闸门去掉；CubeSandbox 的闸门留着。

没有盖住的：默认启动项起不来。那要请负责人从控制台处理。

**二、对公网开口。** 这台机器有公网地址。CubeSandbox 的 API、代理、管理界面、MySQL、Redis 在一键安装的默认配置下没有认证，文档自己提醒上线前要做网络加固。做法（`02-firewall.sh`）：

- 安装之前，在上联网卡上丢掉 ssh 之外的新入站连接（IPv4 和 IPv6；放行已建立的连接、ICMP、DHCP 客户端的端口）；Docker 发布的端口走转发，在 `DOCKER-USER` 链上同样丢掉来自上联的新连接。
- 规则不保存，重启即失效。
- 安装之后从开发机实际探测几个端口，确认外面连不上。
- **没有盖住的一处**：CubeSandbox 会把沙箱的端口映射到上联网卡的宿主端口上，用的是 tc 层的 eBPF，在 iptables 之前。所以沙箱存活期间，它暴露的端口可能从公网连得到。沙箱是 microVM，只在测试的几分钟里存在，端口号是动态分配的。这个风险接受，不处理；做完测试立刻删掉沙箱。
- 实验结束时停掉 CubeSandbox 并重启（见上），规则随重启消失；核对监听的端口回到实验之前的样子。

## 判断次序

- 06 不通过：先看是不是环境的问题（镜像、XFS、DNS、cgroup）。能按安装器的提示解决的解决一次并记下。
- 08 里模板创建不通过：这是 microVM 第一次在 CubeSandbox 的 VMM 上启动。留下 Cubelet 和 VMM 的日志、宿主的内核日志。E1 已经证明这台宿主上 PVM 的 guest 起得来，所以问题在 CubeSandbox 的 VMM 或它的 guest 内核与这个宿主模块的配合上。
- 08 里模板创建通过、从模板创建沙箱不通过：问题在快照恢复。重点看 MSR：E0 测到的 0x3a，以及 #2254 的修复有没有生效。
- 08 通过、09 不通过：microVM 没有问题，问题在代理、DNS 或证书这条数据入口上。记下来，结论写成“沙箱起得来，SDK 的访问路径在这台机器上没有走通”，并说明卡在哪一层。
- 结论只有三种写法：可用（六条都满足）；部分可用（写明哪几条满足）；不可用（写明卡在哪一步和证据）。
