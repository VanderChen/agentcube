# 000-5 的实验记录

每个实验一个目录，目录名是实验的编号。目的有两个：让别人能审计做过什么，让以后能照着重做。这是负责人 2026-11-25 的要求：以文档形式记录实验过程，记下做过哪些操作，便于审计和以后复用。

## 实验一览

都在同一台可丢弃的虚拟机上做（ssh 名 `cpu`：云上的 KVM 虚拟机，AMD EPYC 9845，16 个 vCPU，没有嵌套虚拟化），都在 2026-11-25。

| 实验 | 问题 | 结论 |
|---|---|---|
| [E0](E0/RECORD.md) | 这类机器上 PVM 的宿主能否起来 | 通过。Ubuntu 的 `6.8.0-139` 加 PVM 项目的模块包，有 `/dev/kvm`，Docker 和 Kind 可用 |
| [E1](E1/RECORD.md) | Kata 能否在 PVM 上起沙箱 | **通过。** Kata 4.2.0 配 QEMU、Dragonball、Cloud Hypervisor 都可以，各十次创建、执行、删除全部成功。创建一个沙箱 6.5 到 8 秒；QEMU 的删除偶尔收尾不干净 |
| [E2](E2/RECORD.md) | CubeSandbox 能否在同一个宿主上起沙箱 | **不通过。** 装得上，建模板时 microVM 一启动就复位，换别的 VMM 直接启动它的 guest 内核也一样 |
| [E3](E3/RECORD.md) | CubeSandbox 在它自己的 PVM 宿主内核上 | **通过。** 建模板、从模板建沙箱、执行代码、删除，十次全部成功。创建 79 到 99 毫秒 |
| [E4](E4/RECORD.md) | E2 的失败是启动参数造成的，还是宿主与 guest 要配对 | **只能按原配用。** 启动参数相同时，这两个宿主和这两个 guest 内核只有原配的组合起得来；E2 与 E3 的差别不能用启动参数解释，原因没有查。CubeSandbox 的宿主内核只带 `nokaslr no5lvl` 启动时，CubeSandbox 和换了 guest 内核的 Kata（Dragonball、Cloud Hypervisor）在同一次启动里都起得了沙箱 |

合起来：这台 AMD 机器上 Kata 和 CubeSandbox 都能在 PVM 上用，各自要配它那一边的宿主：

| 宿主 | Kata 4.2.0 | CubeSandbox v0.8.0 |
|---|---|---|
| Ubuntu `6.8.0-139` 加 PVM 项目的模块包 | 可用，三种 VMM（guest 内核用 PVM 项目的） | 不可用 |
| CubeSandbox 的 `6.6.117` 宿主内核 | 照上一格的配置：没有经 Kata 试，直接启动那个 guest 内核约 1 秒后复位。guest 内核换成 CubeSandbox 的之后：Dragonball 和 Cloud Hypervisor 可用（各两个沙箱），QEMU 没有起来 | 可用 |

虚拟机现在停在第一行的状态，怎样切换见 [E3 的记录第 7 节](E3/RECORD.md)。这张表只说这一台机器、这几个版本；为什么只能这样配没有查。E1 到 E3 的记录由子代理复核过，E4 就是为了补它指出的缺口做的；E4 的记录由另一个子代理复核过，各处的说法按它的发现收窄过。

其余的实验（[000-5 的说明](../subtasks/000-5-kata-runtime-spikes.md) 里的 KA-x、KB-x）还没有开始。

## 发布

负责人 2026-11-25 的要求：提交到远端时，因为是公开的仓库，只记录操作，抹掉公钥、地址等隐私信息。

- 公开的副本里有：本文件、`tools/`、每个实验的 `PLAN.md`、`RECORD.md`、`scripts/`，以及 E1 到 E4 的 `commands-as-run.txt`。
- 留在内部、不发布的：原始输出（`log-*.txt`、内核日志、状态记录）、`scripts-as-run/`、E0 逐字的命令导出、机器的只读评估。它们带着机器的标识信息。记录里引用这些文件的地方，在公开的副本里指向的文件不存在。
- 公开的副本里，UUID（根分区、每次启动的标识）换成了 `<uuid>`。
- 公开的副本里，机器镜像原有的几处设置换成了泛指的说法，例如串口控制台参数写成 `console=<原有的串口设置>`。负责人的要求改成了转述，不照抄原话。
- `scripts/` 里是每个脚本最后的版本，多数就是执行的那一份。个别脚本在那个实验里执行的是更早的版本，或者准备了没有用上，各实验记录的第 3 节写明了是哪些；每次执行的 SHA-256 在 `commands-as-run.txt` 里。
- 公开的脚本与内部 `scripts/` 里的逐字节相同，只有三处例外。E0 的 `F-msr-probe.py` 前面加了仓库要求的版权头（仓库的 CI 对所有 Python 文件检查这一条）。E0 的 `G-postcheck.sh` 里，一个网络配置文件的名字换成了通配符。E1 的 `08c-kb1-qemu-journal.sh` 里，查日志的正则里那个四个字母的日志级别缩写写成了等价的 `ERR[O]`，因为仓库的拼写检查会把原来的写法当成错字。`commands-as-run.txt` 里那一行的 SHA-256 对的是执行的那一份。
- 副本由一个内部的脚本生成。它对每个要发布的文件扫描 IPv4 和 IPv6 地址、MAC 地址、密钥和密钥指纹、云服务商的名字、开发机的路径、邮箱；扫到任何一处就不写文件。发布之前另外用机器真实的地址、主机名、密钥、指纹和原始输出里出现过的所有地址与 UUID 逐个对公开的副本查了一遍，没有命中；再由一个子代理独立查了两遍，没有发现隐私数据。
- 原始输出里本来就没有虚拟机和开发机的地址：执行器在写盘之前把它们换掉了。

## 每个实验目录里放什么

| 文件 | 内容 | 什么时候写 |
|---|---|---|
| `PLAN.md` | 目的、通过标准、钉住的版本、步骤、停止条件、判断次序、风险与回退。计划改了就记一条修订 | 动手之前；要改机器的实验先得到负责人批准 |
| `scripts/` | 每一步一个脚本。脚本开头说明它做什么 | 动手之前或当时 |
| `scripts-as-run/` | 执行过的每个脚本版本，文件名前面是 SHA-256 的前八位 | 执行器自动留存 |
| `commands-as-run.txt` | 每次执行一行：UTC 时间、步骤、脚本、脚本的 SHA-256、环境变量、退出码 | 执行器自动写 |
| `log-<步骤>.txt` | 每次执行的原始输出，开头和结尾各有一行带时间的标记 | 执行器自动写 |
| `RECORD.md` | 结论和它的范围；环境与版本（带校验和）；时间线与观察；与计划不一致的地方和意外；对机器的改动与撤销方法；机器的状态；怎样重做；没有验证的 | 做完之后，照日志写 |

E0 是在有执行器之前做的，文件的样子不同，见它自己的记录。

## 工具

| 工具 | 用途 |
|---|---|
| `tools/vmrun.sh <实验> <步骤> <脚本> [KEY=VALUE ...]` | 把 `<实验>/scripts/<脚本>` 复制到虚拟机上以 root 执行；输出、执行记录、脚本的留存都由它写。每次都新开 ssh 连接。输出里虚拟机上联的地址和开发机的地址在写盘之前被换掉，地址在运行时读取，不存下来 |
| `tools/vmwait.sh <实验> <标签>` | 重启之后等虚拟机回来，记下它起来的是哪个内核 |
| `tools/portprobe.sh <实验> <标签> <端口>...` | 从开发机探测虚拟机的端口，确认哪些从外面连得到 |

虚拟机的 ssh 名用环境变量 `VM_HOST` 换，默认 `cpu`。

## 写记录时守的几条

- 命令写成脚本文件，由执行器运行。不在命令行上临时拼长命令，不靠事后导出。
- 改动机器之前先记下改动之前的状态；每个实验结束时做一次只读的状态记录。
- 做错的、没有结论的、事后才核对的，都照实写进 `RECORD.md`，不删日志里对应的段落。
- 外面下载的东西先核对校验和再用，校验和记进 `RECORD.md`。别人的脚本没有许可证的不抄进来，只记 commit 和路径。
- 结论分清三种：测到的、读代码或文档得到的、推断的。别人的脚本报的通过或失败不直接当结论，要看它判的是什么。
- 不记录机器的地址、密钥路径和账号。
- 会让机器失联的操作（换内核、改网络、装会改网络的软件）先想好退路，并且把退路实际走一遍。E2 的计划里有这台机器上用的三样：开机闸门、固定的默认启动项、定时的保险。

## 已经踩过的坑

留给以后重做的人。细节在各自的记录里。

- 脚本用了 `set -o pipefail` 时，`某命令 | head -1` 可能因为 SIGPIPE 让脚本退出；`grep -c` 数到 0 返回 1。用 `sed -n 1p`，或者加 `|| true`。
- PVM 项目的直接启动检查靠 guest 内核横幅里有没有“pvm”来判断，自己编的内核不一定有。
- 防火墙里管 Docker 发布端口的规则要加在 `DOCKER-USER` 链上，这条链在 Docker 启动之后才存在。先启动 Docker，再加防火墙。
- 把 `SSL_CERT_FILE` 指到一张自签的根证书之后，同一个环境里的下载工具就连不上公网的站点了。
- 归因要有对照。E2 把“换了宿主内核就好了”读成了“是内核的问题”，其实两次之间启动参数也变了；复核指出之后用 E4 补了对照。比较两个环境时，先列出它们之间所有不同的地方。
- 保险触发之后会发生什么，要按当时的状态想一遍：E4 里 Docker 的闸门已经去掉，保险如果触发，带自动重启策略的容器会在没有防火墙的情况下起来。
- 有四个脚本版本在留存机制加上之前就被改掉了（E1 的 `01-prepare.sh` 两个，E2 的 `01d-after-boot.sh` 一个，E3 的 `09-quickstart.sh` 一个），只在 `commands-as-run.txt` 里留有 SHA-256；改了什么写在各自的记录里。

机器的只读评估留在内部工作区。
