## 目标

在一个已经有就绪的池的节点上，经节点管理接口发放第一个 microVM：节点适配器调 containerd，containerd 经 Kata 拉起 microVM。

Kata 只提供创建和删除。池的账本、准入、每个沙箱的开销、池级的资源上限，都由节点适配器自己做。这是与计划第一稿最大的不同：那时账本归运行时，适配器只翻译。

## 范围

1. **节点管理接口的服务端。** gRPC，传输凭据可配置，默认 mTLS。
   - 只接受 WorkloadManager 的客户端身份，不是任何同一个 CA 签的证书。基线的 `pkg/mtls` 只校验证书链，身份校验要新加。
   - 监听地址由 `placeholder-agent` 发布到池的状态里；这个地址要能从 WorkloadManager 的 Pod 连到。
   - 证书读不到时拒绝启动。

   第一版实现的方法：
   - `Describe`：运行时的身份与版本（Kata、VMM、containerd）、归属声明、能力集合、接口版本。能力如实声明：只有创建和删除，不声明暂停、恢复、快照。
   - `CreateSandbox`，带等待就绪。
   - `GetSandbox`、`ListSandboxes`。
   - `DeleteSandbox`，幂等，确认之后留下墓碑。
   - `Watch`：池状态必须有；沙箱事件至少有退出。
   - 其余方法返回未实现。
2. **账本与准入。** 适配器自己的，与运行时无关。
   - 每个池记已应用容量和已承诺量。
   - 三个量要分清，换算规则来自 000-5。**声明的规格**是请求里要的 CPU 和内存。**microVM 的配置**是 Kata 实际给虚拟机的 vCPU 和内存：分数核向上取整，内存要加 guest 一侧的开销。**宿主上的预算**是这个沙箱在节点上最多占用的量，还要加上 VMM、shim 等宿主一侧进程的开销。账本记的是宿主上的预算。
   - 准入的条件：承载体在位、池没有在排空、已承诺量加上新沙箱的预算不超过已应用容量。不满足时立即返回“无容量”，不调运行时。
   - 不超分（D15）。
   - 判断和记账在池级的同一个临界区里；容量变更的检查与应用也在这个临界区里（第 3 条）。
   - 预算从准入时起一直占着，直到宿主上的资源确认已经释放：任务已删除，VMM 和 shim 的进程已退出，容器、快照和沙箱的 cgroup 已删除。启动中、结果不明、删除中、已退出但还没收尾的沙箱都占着预算。创建调用返回错误或超时，不等于任务没有起来；收到退出事件，也不等于虚拟机已经清理完。
   - 适配器重启之后，账本从 containerd 的列表和容器上的标签重建，不单靠落盘的数字。
3. **容量变更在真运行时上的实现。** 接口的语义（操作号、围栏、幂等、最近一次操作的记录）在 000-3 和 000-12；这里实现驱动的一侧。
   - 池级的父 cgroup：上限等于已应用容量，放在哪里按 000-5 的结论（D18）。每个沙箱在它下面有自己的 cgroup，上限等于这个沙箱的宿主预算，VMM、shim 等进程都在里面。只有父 cgroup 这一层上限时，一个沙箱越界会连累同池的其他沙箱。
   - 扩容：先放大父 cgroup 的上限，再放大准入的上限。
   - 缩容：已承诺量不高于目标才继续；先把准入的上限降到目标，再降低父 cgroup 的上限。
   - 两步都完成并回读核对之后，才对外报告新的已应用容量。中间失败或崩溃时，对外的已应用容量不变，准入按新旧两个值里较小的一个；重启之后接着做完或回滚。
   - 移除池：池里没有沙箱时删除父 cgroup。
   - 排空是适配器自己的一个标志，落盘。
4. **containerd 加 Kata 的驱动。** 全部运行时专有的代码都在这里。运行时的名字是配置项：开发机填 runc，带 KVM 的机器填 Kata 的那一个。按总体计划的 D22，一套部署里所有节点填同一个；计划作者的建议是适配器把它报告出来，供 WorkloadManager 拿部署声明的运行时核对有没有装错（待定问题 14、17）。
   - 用 containerd 的客户端，在一个独立的 namespace 里操作，不碰 kubelet 的 `k8s.io`。用哪一个 containerd 按 000-5 的结论（D19）。
   - 创建：准备镜像和快照；写 OCI 规格，资源限额按 000-5 的换算规则由声明的规格得出，cgroup 路径是池的父 cgroup 下这个沙箱自己的 cgroup；容器上打标签（池、公开标识、`generation`、租户与归属、声明的规格）；启动任务。
   - 调用方指定的标识就是 containerd 里容器的标识，格式约束按 000-1 的第二批。
   - 就绪：任务进入运行状态。要不要再加一次探测，在实施提案里定。
   - 等待就绪超时之后沙箱保留还是销毁，在实施提案里定。
   - 删除：停止任务，等它退出，删除任务、容器和快照；确认 VMM 和 shim 的进程已经退出、沙箱的 cgroup 已经删除，然后才释放预算、确认删除。
   - 事件：订阅 containerd 的任务退出事件，转成 `Watch` 里的沙箱事件。只有沙箱主进程的退出算沙箱退出；在沙箱里执行的命令退出时也有退出事件，要滤掉。“工作负载已退出”和“资源已释放”是两个时间点：Kata 先发退出事件，再做收尾。
   - 网络：按 000-5 的结论。第一版不要求沙箱能被外面访问。
   - 镜像：第一版按 000-5 的结论，按需拉取或预置；拉取的凭据从节点上的文件读。
5. **适配器的本地状态。**
   - 操作意图日志：调 containerd 之前先落盘。containerd 对重复的标识是拒绝，要靠意图日志把“同一个请求重发”和“标识冲突”分开。
   - 同一个标识和 `generation` 的创建与删除串行处理。删除到达时创建还没做完（例如还在拉镜像），删除先记下墓碑并取消创建；创建在拉完镜像、建容器、启动任务之前各查一次墓碑，查到就停下并清理。删除一经确认，这次创建就不会再留下活着的实例。
   - 墓碑：保留时间取 000-1 的默认值。适配器从没见过的标识被删除时同样记墓碑，迟到的创建会被拒绝。
   - 身份表：公开沙箱标识、运行时一侧的标识、`generation`、归属字段。
6. **重启后的最小恢复。** 适配器重启之后，先用意图日志、containerd 的列表和标签，把自己认领过的实例、身份表和账本重建出来，再核对池的父 cgroup 的上限，然后才重新接受创建。namespace 里有、意图日志里没有的未知实例，第一版只报告，不销毁，但计入已承诺量。
7. **一致性用例。** 同一套用例对假运行时、runc 替身、Kata 都能跑：创建、查询、删除、重复创建、池满、沙箱自己退出、创建中途被删除、删除先于创建到达、启动之后应答丢失、在沙箱里执行的命令正常退出。
8. **一个命令行工具或端到端测试**，直接经节点管理接口创建和删除，并在沙箱里执行一条命令。执行命令的做法：节点上的工具经 containerd 在沙箱里执行，不经适配器的接口。

本子任务分前后两半，各自提交评审、各自验收：

- **000-6A，开发机。** 用 runc 当替身，把发放、池满、删除、重启恢复、容量变更走通。
- **000-6B，带 KVM 的机器。** 把运行时换成 Kata，补上 000-5 第二段指出的差别。

实施提案时如果仍然过大，把账本与容量变更（第 2、3 条）拆成新的子任务。

## 不在范围内

- 暂停、恢复、快照、更新截止时间。Kata 没有这些能力，第一阶段也不要。
- 运行中改沙箱自己的规格。
- 用量记录。
- 节点上的数据入口，以及让沙箱能被外面访问的网络（第二版）。
- 向出口代理绑定网络键；出站网络的策略。
- 对未知实例的销毁性对账（第三版）。
- 承载体长期恢复不了时的限期排空。Kata 不会代做；第一版由人工排空，见 000-3。
- 可续传的事件游标。
- 镜像的分发与缓存策略。
- 接入第二种运行时。驱动的内部接口要保持与运行时无关，但第一版只有一个真驱动。按总体计划的 D21、D22，一套部署只有一种运行时，适配器只有一个驱动：不做按沙箱选驱动；第二种运行时属于另一种部署。

## 开工前要回答的问题

| 问题 | 来源 |

| 沙箱自己退出之后，记录保留多久、容器何时清理、会话怎样得知 | 提案的接口里只有“事件至少有退出” |
| 镜像拉取算不算在等待就绪的时间里；拉取失败用哪个状态码 | Kata 的沙箱就是 OCI 镜像，kuasar 的路线上没有这个问题 |

## 要留好的接缝

编号见 [seams.md](../seams.md)。

- 身份：I-14（创建请求带租户、`generation` 和有类型的归属字段）、I-16（身份表留网络键和运行时化身两栏，第一版为空）、I-19（不把客户端的 metadata 交给运行时；容器上的标签只有适配器自己定义的那几个）、I-20（按命名空间取凭据的函数。第一版只用于镜像拉取，恒返回同一组）、I-21（停止与删除是一串有序的步骤，“向上报告已停止”是最后一步）、I-24（传输凭据可配置）。
- 可观测：O-7（等待就绪的 span）、O-8（trace 上下文经 gRPC 元数据传入；containerd 一侧不延续，把 trace 标识记在容器的标签里）、O-16（身份表在适配器重启后可以重建）、O-17（创建的返回和沙箱事件带阶段时间戳：受理、镜像就绪、任务启动、就绪）、O-19 与 O-20（游标、收尾用量、遥测来源只留字段）、O-23（池的量表与运行时调用的计数、时延，标签里没有沙箱标识）。
- 给第二种运行时留的：驱动的内部接口不出现 containerd 或 Kata 的类型；`Describe` 的能力集合是调用方判断“能不能暂停、能不能快照”的唯一依据。按 D22，一套部署里各池的运行时相同，能力多半也相同；调度器还要不要按能力在池之间挑、“能力不匹配”这个失败原因还要不要，在 000-1 里定。

## 验收

对应里程碑 B，以及第一版 V1-2、V1-5、V1-8 在真运行时上的部分。

**开发机上的 Kind，假运行时。** 一致性用例全部通过。

**开发机上的 Kind，runc 当替身。**

- 池经 000-2、000-3 变为 Ready；命令行工具创建一个沙箱，在里面执行一条命令并取回输出；删除之后 containerd 里查不到它，池的已承诺量归零。
- 沙箱的进程在池的父 cgroup 下；`kubectl get pods -A` 里没有多出 Pod，创建和删除期间没有 Kubernetes API 的写入。
- 用同一个标识和 `generation` 重复创建，得到同一个结果，containerd 里只有一个容器。
- 把池填满之后再创建，立即得到“无容量”，containerd 没有收到调用；已有的沙箱不受影响。
- 删除占位 Pod：新的创建被拒，已有的沙箱存活。
- 带着一个运行中的沙箱重启适配器：沙箱存活；身份表和账本重建出来，已承诺量与重启前相同；之后才重新接受创建。
- 杀掉沙箱的主进程：`Watch` 里有退出事件；收尾完成之后已承诺量才释放。在沙箱里执行一条命令并正常退出：没有沙箱退出事件，已承诺量不变。
- 启动任务之后让应答丢失：已承诺量仍然占着，直到删除完成。
- 创建还在拉镜像时删除：删除被确认之后，containerd 里没有这个容器，之后也不会出现。删除先于创建到达：之后的创建被拒绝。
- 容量变更：父 cgroup 的上限跟着已应用容量变；在改上限的两步之间杀掉适配器，重启之后对外的已应用容量与实际一致。与 000-12 交叉的用例在共同的检查点里验收。
- 用一张不是 WorkloadManager 身份的客户端证书连接，被拒绝。

**带 KVM 的机器，Kata。**

- 上面 runc 替身的用例全部通过。
- 沙箱里的内核版本与宿主不同；microVM 的进程在池所在的 Kubernetes 节点上，进程与 cgroup 的路径记在证据里。
- 沙箱里读到的 CPU 和内存符合 000-5 给出的换算规则。
- 池填满时，节点上各沙箱的实际内存之和不超过父 cgroup 的上限；每个沙箱的 VMM、shim 等进程都在它自己的 cgroup 里；一个沙箱用超自己的预算时，被杀的只是它。
- `Describe` 返回的版本与钉住的 Kata、VMM 版本一致，能力集合里没有暂停、恢复、快照。
