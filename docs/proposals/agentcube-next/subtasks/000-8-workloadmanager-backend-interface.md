## 目标

在 WorkloadManager 里抽出后端接口，现有逻辑原样成为 `pod` 后端。对外行为不变。它是 `pool` 后端的前提，也是第一版里回归风险最高的一步：要改的函数正落在上游改动最频繁的文件上。

基线的现状：没有任何后端抽象；创建、等待就绪、取地址、删除、垃圾回收直接使用 agent-sandbox 的类型，分散在 7 个文件里；会话记录的 `kind` 字段兼作后端判别，未知取值一律按 `Sandbox` 处理。

## 范围

分两步，各自单独提交。

**第一步，只改测试。** 现有 handler 单测用 gomonkey 按名字替换内部函数，而这些正是第二步要移动的函数。先把这些用例改成按 HTTP 行为断言：状态码、响应体、对存储的调用、回滚是否发生。生产代码不动，改完的测试在未改动的生产代码上通过。

**第二步，抽接口。**

1. 后端接口按 000-1 的定义。把创建流程里“建对象、等就绪、取地址”那一段，以及请求删除、创建失败后的回滚、垃圾回收这三处删除，收进 `pod` 后端。
2. 模板解析与构造 agent-sandbox 对象拆成两步；记录的构造函数改为接收与后端无关的结果。
3. 按后端分派：读记录的 `backend`，缺省为 `pod`。未知的取值一律拒绝并告警，不再落入按 `Sandbox` 处理的分支。
4. 垃圾回收经后端执行，后端确认之后才删记录。
5. Router 签发沙箱令牌的函数按后端显式处理。对不认识的后端，不签令牌，也不把调用者的 `Authorization` 转发进沙箱。
6. `main.go` 里控制器的注册按启用的后端组织。
7. 一个后端的删除与垃圾回收能力，同“是否允许用这个后端新建会话”分开注册。000-10 的创建开关关掉之后，存量的池会话仍然要能被删除和回收。

## 不在范围内

- `pool` 后端（000-10）。
- 操作注册表、授权决策的调用点、埋点（000-9）。
- 没有 agent-sandbox 的 CRD 时 WorkloadManager 也能启动（第三版）。本子任务只把结构理顺。
- 给 WorkloadManager 加选主。

## 回归护栏

- 现有端到端测试的两个矩阵作业：经 Router 的创建与调用、直连 WorkloadManager 的创建与删除、warm pool 的领取与归还。
- `pkg/router`、`pkg/store`、`pkg/picod` 的单测原样保留。
- 第一步新写的按行为断言的测试。
- WorkloadManager 的 HTTP 接口也是对外接口，Python SDK 直接调用它。路径、请求体、响应字段、状态码和同步语义的清单见 内部报告 01（基线现状） 第 10.1 节，逐项对照。

## 要留好的接缝

- 未知的后端只有拒绝一个方向。
- 调用者的凭据不进入沙箱。
- 后端接口的每个方法带 `context.Context`，是天然的 span 边界。

## 验收

- 第一步的提交只改测试文件，并在改动之前的生产代码上通过。
- `make test`、`make lint` 通过；现有端到端测试不改即通过。
- 对外接口逐项对照没有变化。
- 在存储里放一条 `backend` 取未知值的记录：删除请求和垃圾回收都不删任何 Kubernetes 对象，也不删这条记录，并留下告警；Router 对它不签令牌，不转发调用者的 `Authorization`。
- 在开发机上的 Kind 上用改动后的构建验证：AgentRuntime、CodeInterpreter、带 warm pool 的 CodeInterpreter 三种会话的创建、调用、删除和空闲回收。
