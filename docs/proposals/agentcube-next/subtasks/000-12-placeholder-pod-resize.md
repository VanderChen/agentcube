## 目标

池已经在用的时候，人工改它的大小，占位 Pod 的 requests 和节点上的池容量按安全的次序跟着变，不重建 Pod，不影响已有的沙箱。

要守住的不变式：承载体在位时，调度器看到的占位 Pod 的 requests 不低于节点上已应用的池容量。扩容和缩容的次序相反，都是为了它：

- **扩容**：先写占位 Pod 的 `/resize`，等 kubelet 分配，再向节点应用更大的容量。
- **缩容**：先向节点应用更小的容量，成功并回读之后，再写 `/resize`。

本子任务只做手工调整（D17）。按需求自动调节、向常规负载让出，在第四版。

## 范围

1. **期望容量从哪里来。**
   - 人工修改池类上的单节点容量。000-2 里这个字段按不可变处理，这里放开：池控制器把新值传到该类每个池的期望容量上，并给每次改动分配一个操作号。
   - 操作号单调递增，一个操作号对应一个目标和一个方向。第一版由池控制器分配；第四版有了容量调节器之后，由调节器写同一组字段。字段的形状按提案的草图，000-1 定稿。
   - 上一个操作没到终态时，控制器不发新的操作号。这期间的人工修改不丢：只保留最新的一个目标，等当前操作到终态之后再下发。例外是可以被取代的操作，见第 5 条。
   - 控制器在每个池上记下已经下发过的是池类的哪一次修改，与目标、操作号、原因一起一次写入。这样控制器重启之后分得清“这个目标已经回退过，不再重试”和“又来了一次新的修改”。期望值与已应用值不相等，本身不触发重试。
   - 回退或被拒绝之后要原样再试一次，或者要撤销一个卡住的操作，走一个明确的人工入口。形式在实施提案里定，建议是池上的一个带序号的注解。控制器据此发新的操作号。
2. **`placeholder-agent` 的调整状态机。** 只有它写 `/resize`。
   - 扩容：写 `/resize` → 阶段 `WaitingAllocation` → 过闸门 → 先把阶段写成 `Applying`，再调 `ApplyPool` → 回读一致 → `Applied`。
   - 缩容：先把阶段写成 `Shrinking`，再调 `ApplyPool` → 回读一致 → 写 `/resize` → kubelet 分配并执行 → `Applied`。
   - 闸门与 000-3 首次应用时的是同一道：Pod 的 generation 已被 kubelet 观察到；没有 `PodResizePending`；容器级已分配的 requests 和 spec 的 requests 都不低于目标。看的是 kubelet 的分配，不是写入成功，也不是调度器的视图。
   - 阶段先写进池的状态，再调 `ApplyPool`；写不进去就不调。agent 不落本地盘。
   - 一个池同一时刻只有一个容量操作。
3. **不成功的几种情形。**

   | 情形 | 处理 |
   |---|---|
   | 扩容时 `/resize` 被 API 拒绝（配额、LimitRange；1.37 上还有超过节点可分配量） | 操作以 `Rejected` 结束，什么都没变 |
   | 扩容被 kubelet 判为不可行（`PodResizePending`，原因 `Infeasible`） | 终态。把 requests 写回原值，操作以 `Reverted` 结束并记下原因。1.35 上超过节点可分配量走的是这一条：写入成功，随后 kubelet 判为不可行 |
   | 扩容被 kubelet 推迟（节点此刻放不下） | 置 `ResizeDeferred`；开始时间和截止时间写进池的状态，agent 重启不重新计时。超时之后把 requests 写回原值，操作以 `Reverted` 结束。回退只允许在调用 `ApplyPool` 之前。不驱逐、不抢占常规 Pod |
   | 缩容时已承诺量高于目标 | 适配器不应用，返回“被推迟”，置 `ShrinkDeferred`；requests 不动，不杀沙箱。这不是终态，适配器不把它当结果缓存：agent 用同一个操作号重试时，适配器重新比较已承诺量，降下来了就应用，并且只应用一次 |
   | 缩容时节点已应用、`/resize` 被 API 拒绝或被判为不可行 | 部分完成：池已经缩小，requests 还没降，不变式仍成立。重试，不进终态。重试无望时经人工入口发一个新操作把容量加回基线（第 1、5 条） |
   | 目标的 cpu 与 memory 一增一减 | 没有安全的次序。agent 拒绝执行，置 `ResourceSynced` 为 False，原因 `MixedDirection` |
   | 运行时一侧的 `Update` 出错（档 1 的 shim） | 扩容照常应用；冻结这个池之后的容量操作并告警 |
   | 操作中途占位 Pod 丢失 | 中止操作，见第 10 条 |

   回退或拒绝之后不自动重试，等下一次人工修改，或者人工入口的重试请求（第 1 条）。

   前提：池所在的节点没有启用 swap。启用了 swap 的节点上，改内存 request 的调整会被 kubelet 判为不可行，缩容会停在部分完成。第一版把它写进安装前提；池控制器能不能从 Node 对象上识别并拒绝在这样的节点上建池，在实施提案里核实。
4. **重启之后接着做。** agent 重启后不从数值推断上一次调用的结果。
   - 状态里的阶段还没到 `Applying` 或 `Shrinking`：没有发出过调用。扩容继续等闸门，或按超时回退。
   - 阶段已到：读适配器的最近一次操作记录。已应用的往下走，已失败的按失败处理，没到终态的等待；适配器没有这个操作号的记录时，用同一份负载重发。
5. **可以被取代的操作。** 有两种。其一，缩容停在 `ShrinkDeferred` 时节点上什么都没应用，人工再改一次期望容量即可取代。其二，`ApplyPool` 的结果在期限内拿不到终态，或者缩容停在部分完成，经人工入口发一个新操作取代，新操作的目标是旧操作的基线。两种情况下控制器都发新的操作号，agent 把旧操作记为 `Superseded`，不再为它发调用；旧操作迟到的调用由适配器按操作号挡住。
6. **节点适配器的容量接口。** 000-3 里操作号固定为初值，这里按真的用：
   - 幂等键是完整负载：池、操作号、目标容量、承载体的 UID、在位标志、排空标志。完整负载相同时返回已有结果。“被推迟”不是结果，不缓存，见第 3 条。
   - 围栏：操作号小于最近一次受理的那个，拒绝。看的是次序，不看那次操作成败。受理时查一次，真正改容量之前再查一次：已经受理、还没提交的旧操作，不能在更新的操作之后生效。
   - 只改承载体信息的调用不是新的容量操作，不改变容量，也不被当作重复而吞掉。它有自己的次序规则：带单调的序号和承载体的 UID，序号更小的、UID 已经作废的都被拒绝。这条规则在 000-1 第一批定义、000-3 实现。这里要保证的是容量操作提交时不覆盖更新的承载体状态。
   - 每个池记最近一次容量操作：操作号、基线、目标、状态。落盘，`GetPoolState` 返回它。
   - 缩容前比较已承诺量，高于目标时不应用，返回“被推迟”。提案用的状态码是 `FailedPrecondition`，取什么由 000-1 定。比较与应用在池级的同一个临界区里，与创建沙箱时的记账互斥。
   - 假运行时支持改容量，可以注入“回读不符”和“应用中失败”。
7. **常驻的巡检。** agent 每次同步拿回读到的池容量与占位 Pod 的 requests、已分配量比较。池容量更高时（占位 Pod 被别人改小，或按更小的规格重建），停止这个池的准入，置 `InvariantViolated`。第一版只做到这里，不自动补偿；唯一的例外是承载体恢复，见第 10 条。
8. **权限。** `placeholder-agent` 的 ServiceAccount 增加池命名空间里 `pods/resize` 的 patch 权限。池控制器仍然没有。
9. **对 000-2 的要求。** 占位 Pod 的规格要让原地调整走得通，并且全程保持 Burstable：requests 写在容器级；只设 requests，不设 limits；cpu 与 memory 的 `resizePolicy` 都是不重启。池命名空间里不能有会注入默认 limits 的 LimitRange，见 000-2。
10. **承载体丢失与恢复。** 操作中途占位 Pod 丢失时：
    - agent 先中止操作，再按适配器的最近一次操作记录把它收敛到终态，并把回读到的池容量写进池的状态。在途的 `ApplyPool` 可能在 Pod 丢失之后才生效，不能凭丢失之前的状态下结论。
    - 控制器重建时，requests 取池状态里的已应用容量；没有应用过时取期望容量。不取期望容量，是因为它可能是一个被拒绝或回退过的目标。
    - 状态里的已应用容量可能是旧的：适配器已经应用，agent 还没写回，Pod 就丢了。这时新 Pod 的已分配量低于回读到的池容量，池不恢复准入。出口是一次承载体恢复操作：只写 `/resize`，把占位 Pod 的 requests 补到回读值，不改池容量，过了闸门再恢复准入。它由控制器按 agent 上报的回读值发号。这是第一版里唯一的自动补偿：没有它，这条恢复路径没有出口。
    - 节点放不下、补不上去时，池保持停止准入，置 `RecoveryBlocked`。之后的处理见 000-3。
    - 原来没做完的目标不自动重做，经人工入口重新发起。

## 与 sandbox-pool 的关系

源码可以复用，但复用不是要求（D9）。这一块重写。路径相对于私有仓库 `kuasar-sandbox/sandbox-pool` 的根，`main` @ `e440730b`。

sandbox-pool 改容量的代码约 1300 行：`pkg/agent/pool_resize.go`、`pkg/agent/pod_spec_updater.go`，以及 `daemon_ttrpc.go` 里处理扩缩的部分。不取用的原因：

- 它用普通的 Pod patch 改 requests，并指望容器被重建之后由 shim 的 `Create` 触发改容量。标准的 Kubernetes 不允许这样改一个运行中的 Pod 的资源；它依赖的是带补丁的环境。
- 它没有“等 kubelet 分配”这一步，也没有操作号。
- 它改的是 kuasar 的配置文件，第一版的运行时不是 kuasar。

两个做法作参考：缩容之前先查已承诺量；被推迟的缩容从池的状态里恢复，不靠 agent 的内存。

- 用准入策略限定谁能写池命名空间里的 `pods/resize`（第三版）。第一版只靠 RBAC。

## 验收

对应第一版的 V1-8。

**开发机上的 Kind，档 0，假运行时。**

- 扩容：改池类的容量之后，占位 Pod 的 requests 先变大，Pod 没有被重建（UID 和容器的重启次数不变）；kubelet 分配之后适配器才收到应用容量的调用；回读一致之后池的已应用容量才变。节点已请求量的增加值等于差值。
- 缩容：适配器先收到应用容量的调用；回读一致之后占位 Pod 的 requests 才变小。
- 缩容时假运行时里的已承诺量高于目标：池置 `ShrinkDeferred`，requests 不变，沙箱记录还在；删掉沙箱记录之后，缩容在同一个操作号下完成，适配器只应用了一次。
- 被推迟的缩容被一次新的人工修改取代：旧操作记为 `Superseded`，池按新的目标走。
- 节点放不下的扩容：池置 `ResizeDeferred`；超时之后 requests 回到原值，操作以 `Reverted` 结束；期间适配器没有收到应用容量的调用，常规 Pod 没有被驱逐或抢占。
- 扩容被推迟期间多次重启 agent：仍然按原来的截止时间回退。
- 超过节点可分配量的扩容：1.37 上操作以 `Rejected` 结束，占位 Pod 没有变化；1.35 上 kubelet 判为不可行，requests 写回原值，操作以 `Reverted` 结束。
- 回退之后池类没有再改、控制器重启：不重发。经人工入口请求之后重发一次。
- 操作进行中又改了两次池类：当前操作到终态之后，只下发最后一次。
- 缩容停在部分完成：经人工入口发新操作，容量回到基线，旧操作记为 `Superseded`。
- 一增一减的目标：没有执行，状态里有 `MixedDirection`。
- 扩容和缩容各一次，在调用 `ApplyPool` 的前后杀掉 agent：重启之后操作走到终态，适配器只应用了一次。
- 带旧操作号的调用被适配器拒绝。已经受理、被拖住没有提交的旧操作，在新操作受理之后不生效。
- 适配器已经应用、池的状态还没写回时，杀掉 agent 并删除占位 Pod：新 Pod 的 requests 被补到回读值之后，池才恢复准入。
- 把占位 Pod 手工改小：池停止准入，置 `InvariantViolated`。
- 调整期间池一直可以准入（按已应用容量），假运行时里已有的沙箱记录没有变化。
- 池控制器的 ServiceAccount 写 `pods/resize` 被拒绝。

**开发机上的 Kind，档 1（000-4 通过时）。** 扩容和缩容各一次，结果与档 0 相同，节点上没有多出进程。

**真驱动检查点（与 000-6 的驱动一起，开发机用 runc 当替身，带 KVM 的机器用 Kata）。**

- 带着一个运行中的沙箱扩容和缩容：沙箱存活；池级 cgroup 的上限跟着已应用容量变。
- 扩容之后能多放下一个沙箱；缩容之后放不下的创建得到“无容量”。
- 已承诺量高于目标的缩容被推迟，沙箱没有被杀。
- 缩容的检查与一次并发的创建交错：结果要么是创建成功而缩容被推迟，要么是缩容完成而创建得到“无容量”，不会两者都成功。
