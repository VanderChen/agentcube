## 目标

经 AgentCube 的原生创建接口发放 microVM。第一版的准出在这里。

入口是 WorkloadManager 的创建接口，Python SDK 今天就是这样创建代码解释器会话的。Router 的转发逻辑不动；经 Router 访问池会话的数据面在第二版。

## 范围

1. **`pool` 后端与最小的创建事务。**
   - 创建分四步：写占位记录；放置；**每次向节点提交之前**，先用条件写把这次尝试的目标节点、池、沙箱标识、`generation` 和尝试状态写进记录；提交成功后把数据入口地址、实际资源、启动路径写进记录，状态转为就绪。先记目标再提交，是为了在 WorkloadManager 崩溃之后还能找到那个节点。
   - 确定的失败（无容量、池不可用、能力不匹配、没有候选）：释放占位记录，并清理运行时里留下的失败实例。
   - 结果不明（断连、超时）：不删记录，标为“未知”并钉在原节点；向原节点发删除并等确认之后才允许重新放置。删除的确认意味着原来那次创建不会再留下活着的实例，这一点由节点适配器保证（000-6 的墓碑规则），本子任务依赖它。
   - 重启之后：处于“已记目标、结果未定”状态的记录，按“结果不明”处理。
   - 创建请求阻塞到就绪才返回，与现有语义一致。就绪以节点适配器的等待就绪为准；现有创建流程对沙箱入口做的 TCP 探测要求 WorkloadManager 能直达沙箱地址，池路径不做。
   - 删除：调节点管理接口，后端确认之后才删记录。垃圾回收经后端执行。
   - Kata 不返回任何令牌。接口里的令牌字段留着，第一版为空；以后有值时不持久化，不进日志。

   这是创建路径自己的一致性，不是第三版的多副本提交协议，也不是完整的库存对账。
2. **沙箱调度器与到节点的连接。** 调度器是 WorkloadManager 进程内的库，接口独立。
   - 池目录：池对象的 informer，加上到每个池的节点适配器的一条池状态流。流中断时该池移出候选。
   - 连接：从池的状态里发现适配器的地址；用 WorkloadManager 的客户端证书建立 mTLS，并校验适配器证书里的节点身份与池所在的节点一致。
   - 过滤：池的 Phase 是 Ready、承载体在位、没有排空、适配器报告可准入、命名空间被池类允许、粗估有余量。不打分。余量按期望容量和已应用容量里较小的一个估：缩容一下发，调度器就不再往要让出的那部分里放（000-12）。
   - 候选逐个提交。适配器答“无容量”就换下一个；都不行就向客户端返回无容量。调度器不排队、不等待。
   - 构建依赖里没有 Volcano、`k8s.io/kubernetes` 和运行时的模块。
3. **沙箱退出与到期的处理。** 消费池状态流里的沙箱退出事件：沙箱自己退出之后，经条件写推进会话的状态并确认删除，同时产生生命周期事件。Kata 没有到期删除，到期由 WorkloadManager 的垃圾回收经后端执行。重复的事件不重复推进，也不重复追加发件箱条目。
4. **模板。** 池模板的定义和校验按 000-1。现有的 `CodeInterpreter` 控制器遇到池模板时要分叉：不创建 agent-sandbox 的模板和 warm pool 对象，不依赖 Router 的签名公钥。公开沙箱标识的生成也在这里。
5. **创建开关与存量处理分开。**
   - “允许创建池会话”是一个开关，默认关闭。
   - 池会话的删除、垃圾回收、退出事件处理不受这个开关控制：只要这个版本认识池后端，就一直处理存量。
   - 写明启用、关闭、回滚的规程。启用：全部 WorkloadManager 和 Router 副本已是新版本。关闭：停止新建，存量照常处理。回滚到不认识池后端的版本：先关开关，清空池会话，确认为零之后才回滚。旧版本的垃圾回收遇到池会话的记录，会把记录删掉而不销毁 microVM，所以这一步不能省。
   - 000-7 如果决定让池会话不进旧垃圾回收读的索引，规程相应放宽。
6. **接缝的贯通。** 主体和归属字段随创建请求到达节点适配器；trace 延续到节点适配器，含等待就绪；生命周期事件带各阶段耗时。
7. **权限。** WorkloadManager 对池类与池只读。

本子任务有一个内部检查点，可以分两次提交评审：先是池目录与到适配器的连接，再是创建事务。实施提案时如果仍然过大，把前一半拆成新的子任务。

## 不在范围内

- 多个副本并发创建时的提交协议与在途量、打分、放置画像（第三版）。
- 暂停与恢复、设置超时。
- 完整的库存对账、对未知实例的清理（第三版）。
- 经 Router 的数据面、E2B、访问令牌（第二版）。

## 验收

对应第一版的 V1-4、V1-5、V1-6，以及 V1-7 里可运行验证的部分。

**开发机上的 Kind，假运行时。**

- 开关关闭：现有端到端测试不改即通过；不产生池会话。
- 开关打开：经创建接口创建一个池会话，记录为就绪，带后端、池、节点；删除之后记录不在了，假运行时的账本归零。
- 开关先开后关：不能再新建池会话；已有的池会话仍然能被删除，到期后被回收。
- 池模板不产生任何 agent-sandbox 对象；Router 的签名密钥不存在时，池会话照样能创建。
- 池满：创建立即返回无容量，占位记录被释放。有两个池时，第一个满了，创建落到第二个。
- 缩容已经下发、节点还没有应用时：调度器不再往超出新目标的余量里放。
- 创建与删除期间，API server 的审计日志里没有来自 WorkloadManager 的按会话写入，也没有新增的 Kubernetes 对象。
- 三种中途失败，假运行时注入：
  - 节点受理之后断连：记录被标为“未知”，带着目标节点；向原节点的删除得到确认之后才允许重新放置。
  - 节点返回成功之后写存储失败：实例没有成为无主的，后续的删除能把它清掉。
  - 向节点提交之后、收到结果之前重启 WorkloadManager：重启后的进程从记录里找到目标节点并按“结果不明”处理。
- 假运行时报告一个沙箱退出：会话被推进到已删除，有一条生命周期事件；同一个事件重复到达不产生第二条。
- 用一张节点身份不符的适配器证书：WorkloadManager 拒绝连接，该池不进候选。
- 新旧版本交叉：有池会话存在时启动一个旧版本的 WorkloadManager，把观察到的行为记下来，用来核对回滚规程写得对不对。
- 一次创建是一条从入口到节点适配器的 trace，含等待就绪；每次状态变化有一条生命周期事件。

**开发机上的 Kind，runc 当替身。**

- 同样的创建：沙箱的进程在池所在的节点上，在池的父 cgroup 下；节点上的工具经 containerd 在里面执行一条命令并取回输出；删除之后 containerd 里查不到它，池的已承诺量归零。
- 把池填满之后再创建，客户端立即得到无容量；已有的沙箱不受影响。
- 删除占位 Pod 之后的创建被拒；占位 Pod 恢复并过了分配闸门之后，创建重新成功。
- 手工把池扩大之后，原先放不下的创建成功。

**带 KVM 的机器，Kata。**

- 上面 runc 替身的用例全部通过。
- microVM 的进程在池所在的 Kubernetes 节点上运行，进程与 cgroup 的路径记在证据里；沙箱里的内核版本与宿主不同。
