# 000 方案 gap 分析与计划依据

状态：**规划阶段，等待确认**。agentcube 的代码没有改动。本文是开发计划（[README](README.md)）的依据。分析由计划作者和它调度的六个只读子代理完成；子代理的报告留在内部工作区，没有随本分支推送，文中称为“内部报告”。

全部结论来自静态阅读：读了提案、agentcube 基线、sandbox-pool、上游 PR #431、kuasar-sandbox 与 CubeSandbox 的源码和文档，以及此前已有的 Kata 研究笔记。没有构建、部署或运行任何东西。

本文写过两稿。第一稿把首个运行时建议为 kuasar-sandbox。2026-11-24 负责人确定了新的方向：第一阶段放弃快照管理这一类事情，先把占位 Pod 的流程走通，包括占位 Pod 的 resize；运行时取 containerd 加 Kata。第二稿据此改了第 1、3.3、3.6、4、7 节，第 6 节末尾说明评审处置里哪些被替换。

## 1. 结论

1. **提案是静态设计，离代码还有一层定义要补。** 接口、对象、流程都是示意；65 个实验一个没做；有七条未决问题直接卡住第一版。所以第一个子任务是把定义定稿（000-1）。
2. **agentcube 基线里，节点一侧是空的，控制面一侧没有后端抽象。** 池控制器、占位运行时、`placeholder-agent`、节点适配器、沙箱调度器都没有。WorkloadManager 直接使用 agent-sandbox 的类型，分散在 7 个文件里；会话记录的 `kind` 字段兼作后端判别。
3. **sandbox-pool 只覆盖占位 Pod 这一半，而且是原型。** 它没有任何创建沙箱的代码。它与提案相同的是 API Pod、Phase 聚合、Lease、finalizer；相反的是多池加副本数、没有分配闸门、不处理承载体丢失、写完配置即认为生效。它没有 LICENSE 文件；负责人已确认源码可以复用，但复用不是要求，所以按组件取舍：池类控制器、池控制器的大半、shim 的握手与状态机值得移植，其余新写。
4. **“发放 microVM”这一半没有先例，取决于运行时。** 运行时现在是 containerd 加 Kata。Kata 只提供创建和删除，没有面向用户的沙箱接口，也不做节点级的记账；账本、准入、每个沙箱的开销都归节点适配器。第一稿选的 kuasar-sandbox 有自己的账本和最短路径的参考实现，但改容量要重启 conductor，容量拒绝是异步的、没有机读原因。
5. **开发机不能起 Kata 的 microVM，但能做的比第一稿多。** 开发机没有 KVM，Kata 要 `/dev/kvm`。占位 Pod 的各层和原地调整与运行时无关，可以在开发机上的 Kind 上做；节点适配器调的是 containerd 的接口，发放路径可以先用 runc 当替身在开发机走通。后一点是分析，由 000-5 确认。
6. **身份与可观测在基线里几乎是空白，这反而让第一版留接缝的代价很小。** 没有租户、没有绑定沙箱的令牌、没有指标和 trace。提案分析把两条线各归为五处接缝，合计 52 条可检查的要求。
7. **计划因此分成三条可以并行的线和三个里程碑。** Kubernetes 一侧在开发机先做；控制面一侧先做不改行为的重构；运行时一侧先在开发机用 runc 当替身，Kata 的部分等带 KVM 的机器。
8. **resize 进了第一版，它在两种运行时上的难度相反。** kuasar 上改容量是一次 conductor 重启。账本归节点适配器之后，改容量是改账本上的数字和一个父 cgroup 的上限；难处移到了 Kubernetes 一侧：`/resize` 与 kubelet 分配的先后、被推迟时的回退、操作号与围栏。提案对这部分有完整的设计，但实验一个没做。

## 3. 方案 gap

### 3.1 提案与 agentcube 基线

详见内部报告 01（基线现状）第 11 节。模块编号是提案的编号。

| 模块 | 基线已有 | 缺口 | 第一版的切口 |
|---|---|---|---|
| M1 Router | 原生 invocations 路由；可选 OIDC；所有者比对；按会话记录里的地址反向代理。数据请求路径已经不调用 Kubernetes API | 操作注册表；按后端签发令牌；E2B 监听器；指标与 trace | 转发逻辑不动。必须改一处：签发沙箱令牌的函数只认两种 `kind`，新后端的会话会让调用者的 `Authorization` 原样进入沙箱 |
| M2 WorkloadManager | 创建、删除、垃圾回收、warm pool 控制器 | 没有后端接口；没有 leader election；agent-sandbox 的 CRD 缺失时进程约两分钟后退出（按相邻版本推断，没有运行） | 把创建里“建对象、等就绪、取地址”那一段和三处按 `kind` 的删除收进接口，现有逻辑成为 `pod` 后端 |
| M3 沙箱调度器 | 没有，放置完全交给 Kubernetes | 全部 | 新写一个包，作为 `pool` 后端的内部依赖 |
| M4 会话存储 | 9 个方法的接口；Redis 与 Valkey 两个实现；两个全局索引 | 没有比较并交换和事务；写入用普通管道且不检查 `SETNX` 的结果；多键操作与集群模式不兼容；没有按池、命名空间的索引 | 加字段向后兼容；风险在索引和原子性 |
| M5 池控制器 | 没有 | 全部 | 独立的二进制和 Deployment，不放进 WorkloadManager：后者没有 leader election，权限也不该扩大 |
| M7 占位运行时 | 没有。唯一相关的是一个不生效的参数 `--runtime-class-name` | 全部 | 档 0 不需要代码 |

| M9 节点适配器 | 没有。可复用的是 `pkg/mtls` | 全部 | 新的二进制 |
| M11 guest 守护进程 | PicoD，不依赖 Kubernetes | 它的接口是 AgentCube 私有的，不做沙箱绑定校验 | 第一版用运行时模板里自带的守护进程，不打包 PicoD |
| M12 身份与策略 | 可选的认证加一条所有者比对；`admin` 字面量旁路；没有租户 | 见 3.5 | 只留接缝 |
| M14 可观测 | klog 文本日志；健康检查端点 | 见 3.5 | 只留接缝 |

回归面上三处最要紧的事实：

- **WorkloadManager 的 HTTP 接口也是对外接口。** Python SDK 直接调用它创建和删除会话，所以它的路径、请求体、响应字段和同步语义都要保持。
- **现有 handler 单测不能原样当护栏。** 它们用 gomonkey 按函数名替换内部函数，而这些正是抽接口时要移动的函数。要先把测试改成按行为断言，再动生产代码。
- **没有任何升级或兼容性测试。** Router 与 WorkloadManager 分别滚动升级时，新旧版本会同时读写同一份会话数据。旧版本的垃圾回收遇到池会话的记录，会把记录删掉而不销毁 microVM。所以 `pool` 后端要有开关，并且只在全部副本升级之后打开。

与报告 02 的口径差别最大的是 `placeholder-agent`。报告把它的四个大文件归为“改造后移植”，同时也写了“M8 只剩骨架”。逐函数看，要留的骨架（监听、看门狗、断线重连，约 270 行）建在动态客户端、非结构化对象和标签选择上；提案要的是按节点名选池、同时监听 Pod，agentcube 已经在用 controller-runtime 并且会为新的 API 组生成有类型的客户端。在这个基础上新写，比把现有骨架改过去省事，也不会把多池和 node-ctl 的假设带进来。

不论取哪一段，下面这些与许可无关的成本都在：

- 手写的 deepcopy 与 CRD 清单不能用，改正类型上的标记之后用工具生成。
- 它用了三个已标为弃用的 controller-runtime 接口，移植时换成新的。
- 日志接口统一成 klog；清单改写成 chart 模板；每个文件补上 agentcube 的文件头。
- shim 要引入 containerd v2 的一组依赖，放进单独的 Go 模块。
- `pkg/internal/apikey` 是从 kuasar 的 orchestrator 内部包拷来的，不取用。


**隐含假设。** 它的代码和文档里普遍带着三个假设：kubelet 会重建容器；node-ctl 会热加载配置；一个节点可以有多个池。移植时要逐处剔除。它的文档与代码有多处不一致，以源码为准。

### 3.3 提案与运行时

| 方面 | 提案对运行时的假设 | Kata 上的事实 | 对计划的影响 |
|---|---|---|---|
| 对上的接口 | 节点上有一套节点栈，有自己的沙箱接口 | 没有面向用户的“创建沙箱”接口，只有 containerd 的 shim 接口。containerd 为每个沙箱起一个 shim 进程，shim 起一台虚拟机。不依赖 Kubernetes | 节点适配器经 containerd 调用。标识、幂等、状态都由适配器管 |
| 设定池容量 | 一次幂等的调用，回读确认 | 没有池的概念，没有节点级的账本 | 账本归适配器。改容量不重启任何东西，所以 resize 可以进第一版 |
| 创建时的容量准入 | 池满时创建被拒 | 不做 | 适配器在调 containerd 之前同步判断，立即返回无容量。V1-5 不再依赖运行时的判据 |
| 生命周期 | 暂停、恢复、快照是可以声明的能力 | 只有创建和删除。它的暂停与恢复是沙箱里的 cgroup 冻结，虚拟机照常运行；没有 checkpoint；虚拟机模板只有 QEMU、Cloud Hypervisor、Dragonball 有，Firecracker 没有 | 第一阶段放弃这些能力，`Describe` 如实声明没有 |
| 虚拟机的规格 | 沙箱的规格等于声明的规格 | 默认 1 个 vCPU、2048 MiB，内存不预分配。默认的 Rust 运行时在启动前定规格：有限额时是限额加一份开销，没有限额时用默认值 | 适配器要在 OCI 规格里写限额。每个沙箱的固定开销要实测（000-5），账本按“声明的规格加固定开销”记 |
| VMM | — | Firecracker 在 Kata 的打包里走已经弃用的 Go 运行时，要块设备快照器，不能热增减 CPU 和内存。Cloud Hypervisor、Dragonball 走默认的 Rust 运行时 | VMM 由实验定（000-5） |
| 宿主上的 cgroup | 节点栈自己限制沙箱的总量 | 布局随运行时和一个配置开关而不同；Kata 不限制一组沙箱的总量 | 适配器为每个池建一个父 cgroup（D18），做法由 000-5 确认 |
| 网络 | 运行时带数据入口 | 调用方准备网络命名空间；不支持宿主机网络；没有数据入口，没有出站策略 | 第一版不要求从外面访问沙箱；第二版自建数据入口 |
| 沙箱的内容 | 运行时一侧的模板 | 就是 OCI 镜像 | 与 agentcube 现有的镜像模板对得上，不需要模板构建管线 |
| 环境 | — | 要 `/dev/kvm`。Kata 自己的仓库里没有提到 PVM，也没有纯软件模拟的路径。PVM 是 KVM 的一个厂商模块，装上之后有 `/dev/kvm`，见下面“没有 KVM 的虚拟机” | 开发机用 runc 当替身；Kata 在带 KVM 的机器上验证 |

“不经 CRI、直接经 containerd 的原生接口使用 Kata”这一用法，Kata 的研究里没有专门核对，见第 7 节。有一个旁证：PVM 项目测试 Kata 时用的就是 `ctr run --runtime io.containerd.kata.v2`。

**沙箱的网络：connector 作为候选（2026-11-25）。** 负责人问讨论材料里的形态 B 和形态 C 能不能由一个 connector 管网络。connector 是 kuasar-sandbox 的节点交换机。计划作者读了它的 `README.md`、`docs/vswitch.md`、`docs/vswitch-operations.md`、`docs/tapfd.md`、`LICENSE_SCOPE.md`（`6b48c8f`），以及 Kata 两个 runtime 扫描网络命名空间、接 veth 的代码（`2e1efbe1`）；没有运行。结论：取 kuasar-sandbox 的形态 C 本来就用它；按静态阅读，形态 B 可以用它的 veth 端口，没有人验证过；取 CubeSandbox 的形态 C 换不了。

| 方面 | connector 上的事实 | 对形态 B 的含义 |
|---|---|---|
| 能不能单独用 | README 写明它可以单独部署，并经 TAP 文件描述符的交接约定配别的 microVM 运行时；适用的场景写的是单机上用 Firecracker、Cloud Hypervisor 或 QEMU 的 microVM 平台。veth 端口是文档里的另一种端口形态，默认是 TAP；上游没有把 veth 写成接别的运行时的途径，读到的使用方只有走 TAP 的 sandboxer | 不用装 kuasar-sandbox 的其余部分。但形态 B 走的不是上游写明的那条集成途径 |
| 端口的两种形态 | TAP：交换机留着 TAP 设备，把队列的文件描述符经 Unix socket 交给 VMM。veth：`attach --to-netns` 把 veth 的一端移进沙箱的网络命名空间 | Kata 没有实现 TAP 描述符的交接，两个 runtime 的网络代码里都检索不到。两个 runtime 都扫描命名空间里已有的网卡，用 TC 过滤器把 veth 接到自己的 tap 上，guest 的网卡取 veth 的 MAC。所以用 veth 端口，不用改 Kata；runc 替身同样适用 |
| 端口设备回收再用 | attach 和 detach 不建也不删端口设备，同一个 veth 在沙箱之间反复使用；命名空间先于 detach 被销毁，会留下一个占着的端口 | Kata 是按每次新建 veth 的用法写的：它在 veth 上加自己的 qdisc 和过滤器，只在正常拆除时删；runtime-rs 遇到别人留下的 qdisc 会让接入失败。shim 异常退出之后的残留会不会挡住同一个端口的下一次接入，没有验证。适配器要在 detach 之前清掉，并且先 detach 再删命名空间 |
| 给什么 | 每个沙箱一个端口，没有端口到端口的转发；端口由入口设备认定，不信 guest 自报的地址；每次附着有一个浮动地址，里面的代数由调用方给，默认的位宽是 0；节点上管理命名空间里的服务经浮动地址进出沙箱，这条路上有无状态的地址改写 | 沙箱之间默认不通。与 kuasar-sandbox 能用同一套的是寻址和网络身份；数据入口这个部件仍要自建，kuasar-sandbox 的入口是它自己的 Proxy。浮动地址可以作第二版数据入口的目的地址。作出站归属的键有两条保留：走 GENEVE 网关时，网关看到的是端口的定位和 VNI，不是浮动地址；端口一回收地址就会重复，代数要由适配器管，够不够用没有核实 |
| 不给什么 | 没有连接跟踪、有状态的 NAT、限速和 L7 过滤。出站是封装成 GENEVE 交给外部网关，或者把流量抽取到运维自备的出口命名空间。节点本地的出站策略面还是上游的一个提案 | 出口代理或外部网关仍然要有，第四版的出站策略不因为它而省掉 |
| 限制 | 每个交换机最多 4096 个端口，编译期定死；一条上联；要 root；文档写的内核基线是 5.10，要 BTF 和 bpffs；控制只限于交换机所在的那台主机，没有跨主机的状态同步。要出站就要一块专用的上联网卡，启动时必须是 DOWN，会被移进交换机的命名空间。管理面的抽取网段在启动时定死，每个端口最多 3 段，改它要重建交换机；数据面的 ABI 变了也要重建，没有在线迁移 | 进安装前提。Kind 节点的容器里能不能加载它的 eBPF 程序没有验证 |
| guest 里的地址 | 沙箱的内层地址由调用方在附着时给；connector 不配置 guest | 适配器要在创建任务之前，在命名空间里把地址和路由配到 veth 上：没有地址的网卡 Kata 会跳过。Kata 再把它们带进 guest。这一步没有验证 |
| 许可证 | Go 代码是 Apache-2.0；eBPF 程序和编译出的对象是 GPL-2.0-only，对象放在它的一个 Go 包里 | 工程上稳妥的做法是把 `connector-ctl` 当独立的程序调用，不把带这些对象的包编进 AgentCube 的二进制。许可证上是否必须这样，没有做判断 |

取 CubeSandbox 时换不了：它的网络是 CubeVS，TAP 取自 Cubelet 预建的池，由 Cubelet 的创建流程直接调用；不改它的代码就接不进 connector。所以“一个 connector 管两种形态”对形态 B 和取 kuasar-sandbox 的形态 C 成立。

它在计划里的位置：是第一版沙箱网络的一个候选（D20），不是已定的选择。000-5 增加实验 KA-7，并在 KB-7 里加上它。第一版只要求节点上可达，不取决于这一项；第二版的数据入口和第四版的出站归属受它影响。

**没有 KVM 的虚拟机：Kata 与 kuasar。** 开发机就是这类机器。这类机器上要起 microVM 只能靠 PVM。负责人在 2026-11-24 要求：Kata 也不支持这类虚拟机的话，看看 kuasar。静态核对的结果是 Kata 有路，kuasar 的处境更差。

| | Kata | kuasar-sandbox |
|---|---|---|
| PVM 一侧的依据 | PVM 项目的说明写的是它为了在没有硬件虚拟化的情况下支持 Kata 而做，并附运行指南。发布宿主模块包时的测试包含 Kata 配 QEMU、Dragonball、Cloud Hypervisor，用 Rust 运行时；v0.1 的发布说明称六个目标系统全部通过 | 没有。内部工作区里它的九个仓库（含 Cloud Hypervisor 分叉）检索 `pvm`，零命中，2026-11-24 重新检索过 |
| guest 内核 | 换成 PVM 项目的 6.12 内核，改 Kata 配置里的一个路径。指南要求 Kata 不低于 3.14 | 自带的是 6.1.169 加两个补丁。PVM 的 guest 支持只有 6.6、6.7、6.12 三条线，要在 PVM 的内核树上重新编译并移植补丁 |
| 运行时的代码 | 不用改 | 要改：根文件系统是 pmem 设备，PVM 下要把 guest 的地址宽度限制在 43 位，它的 `sandbox-ctl` 没有这一步 |
| VMM | QEMU、Dragonball、Cloud Hypervisor。Firecracker 不在测过的 Kata 组合里 | Cloud Hypervisor 的分叉，版本够新，但 14 个补丁里没有与 PVM 有关的 |
| 先例 | PVM 项目的测试 | 没有 |

两者共同的条件在宿主一侧：装 PVM 的内核模块（或换 PVM 的宿主内核），带关闭 KPTI、KASLR 一类的启动参数重启。现成的模块包只对应确切的内核版本，Ubuntu 24.04 上是 `6.8.0-139-generic`，开发机是 `6.8.0-149-generic`。PVM 项目说 AMD 的机器要另外取证，开发机是 AMD 的虚拟机。

开源的 Kuasar（`kuasar-io/kuasar`）在 GitHub 的代码和 issue 检索里也没有 PVM 的命中；它的 microVM 沙箱用 Cloud Hypervisor、StratoVirt、QEMU，Quark 沙箱按它自己的说明要起 KVM 虚拟机。

所以“Kata 不行就换 kuasar”在这类机器上不成立。Kata 在 PVM 上不通过时，先分清是机器跑不了 PVM，还是 Kata 的问题；是后者，再评估为 kuasar 做移植，次序在 000-5。kuasar 一侧的细节见内部报告 03（运行时调研）第 6.6 节。

**kuasar-sandbox（第一稿的选择，现在是带快照的第二种运行时的候选）。** 详见内部报告 03（运行时调研）第 2、3、5 节。下表“对计划的影响”一栏写的是第一稿的计划，留作对照。

| 方面 | 提案的假设 | 当前版本上的事实 | 对计划的影响 |
|---|---|---|---|
| 设定池容量 | 一次幂等的调用，回读确认 | 容量写在配置文件的 `resource_listen.pools[]` 里，conductor 只在启动时读一次。改容量就是重启 conductor：运行中的 microVM 存活，在途的创建失败 | 第一版池大小固定，重启只在建池时发生一次，那时池里没有沙箱。运行中改容量留到第四版 |
| 创建时的容量准入 | 池满时创建被拒，状态码是资源不足 | 准入在运行时一侧，但分两段。同步段只看排空和水位，不比较大小。数量比较在返回“已受理”之后，失败表现为沙箱从 starting 变成 dead，接口不给机读的原因；放不下时还可能先排队最长 30 秒。默认超分时，运行时还可能在内存压力下暂停别的沙箱 | 适配器的“等待就绪”要负责翻译；判据先由实验确定，000-5 是硬闸门。第一版关闭超分（D15） |
| 就绪 | 同步，或异步但可观察 | 异步。可以轮询，也可以订阅；订阅没有可续传的游标，并且会下发租户凭据 | 第一版用轮询 |
| 沙箱标识 | 调用方指定 | 可以，1 到 57 字节的小写字母、数字、连字符。没有 `generation` 的概念，标识在记录清理完之前不能复用 | 公开沙箱标识的格式和 `generation` 的映射要在 000-1 里定 |
| 节点上的形态 | 节点适配器是宿主机服务，只经它到达运行时 | 上游的系统容器镜像不能原样作为 Pod 运行；conductor 的本地 socket 在那个容器内部 | 适配器装在哪里要先做实验（000-5） |
| 出站 | 选 kuasar 时出站网关作为条件项进阶段一 | 默认没有 guest 出站；入站、原生 exec 和管理面通信仍可用 | 发放一个 microVM 不需要出站，第一版不做 |
| sandbox-pool 与 kuasar 的对接 | — | 只有“读状态”和“排空”两个调用与当前版本一致。它假定的热加载、把容量写成 0 表示待机、配置里的 `proxy.mode` 在当前版本上都不成立，后两者会让配置加载失败 | 写容量的部分重做 |

接入契约前 9 条在 kuasar 当前版本上的核对结果：第 1、2、3、4、6、8 条有源码或文档依据；第 5 条有，但是异步的；第 7 条里“数据入口不放行守护进程的内部路径”没有核实；第 9 条能轮询也能订阅，是否足以实现事件流没有核实。“有”指读到了源码或文档，不是测试通过。

| 方面 | 基线 | 提案要到达的状态 | 第一版 |

| 生命周期事件 | 没有 | 与状态变更同一个原子写入，至少一次投递 | 结构就位，尽力而为地发成日志 |
| 审计、计量 | 没有 | 第四版 | 只留字段 |

sandbox-pool 在这两条线上可以借用的是：只打在池对象上的事件、有界的指标标签、Lease 存活信号。与提案相抵、不能带过来的是：所有节点共用一个身份、十年期的静态令牌、API 里绑定一种运行时的名字（`nodeCtl`）、租户与凭据走 kuasar 的模型。

### 3.6 验证环境

- 开发机：没有 `/dev/kvm`，CPU 没有虚拟化标志；Docker、kind v0.33.0、kubectl、helm 可用。kind 的默认节点是 Kubernetes v1.37.0 和 containerd 2.x：原地调整 Pod 资源自 v1.35 起稳定，空操作 shim 需要的 containerd 2.0 也满足。
- agentcube 现有的端到端测试里没有任何 microVM 运行时，也不安装 Volcano。
- 提案没有讨论开发与测试环境。旧路线里“一个测试用的假实现通过同一套端到端用例”没有带进本专题的准出标准；本计划把它带回来，作为开发机上的 Kind 上的验证手段（000-3、000-6、000-10 的假运行时）。
- 内部工作区规则要求代码改动在 Kind 上验证。microVM 相关的验证只能在带 KVM 的机器上的 Kind 或单节点集群里做。
- 可丢弃的虚拟机（2026-11-25）。负责人提供了一台可以换内核的虚拟机，计划作者只读地查过。它与开发机同一个发行版和内核版本，同是 AMD，同样没有嵌套虚拟化和 `/dev/kvm`；CPU 不是同一代。第一段的实验可以在它上面做。它不是带 KVM 的机器，Kata 的 microVM 要先过 E0、E1。E0 的条件比原先设想的好：Ubuntu 的软件源里还有 `6.8.0-139` 的内核包，PVM 项目 v0.1 的模块包正是为它构建的，计划作者核对过包的校验和与内容；所以不用换成别家发行版的内核。评估时没有解决的是 AMD：PVM 项目说 AMD 的机器要另外取证，这台机器开着五级页表，这两点上没有读到验证记录。评估记录在 000-5 的任务目录里。
- E0 的结果（2026-11-25，测到的）。负责人批准之后，计划作者在这台虚拟机上做了 000-5 的 E0，四条通过标准都满足：换到 `6.8.0-139-generic` 加 `nokaslr` 之后能登录（kexec 和冷启动各一次）；加载 PVM 的模块之后有 `/dev/kvm`；内核日志没有错误；Docker 和 Kind 可用。五级页表不碍事。它只到宿主一侧，没有运行任何 guest，所以 AMD 上 PVM 能不能跑起 microVM 仍然没有证据，要等 E1。顺带测到 `kvm-pvm` 在这台 AMD 宿主上拒绝给 vCPU 写回 MSR 0x3a，与第 4.2 节提到的“CubeSandbox 在 AMD 的 PVM 主机上创建失败”的原因描述一致（内部报告 03（运行时调研）第 6.5 节记的原因就是 `kvm-pvm` 拒绝写回这个 MSR）；做内存快照恢复的路线要把它当作已知条件。这台机器的默认启动项没有改，PVM 宿主要用一次性的启动项进入。操作记录在 000-5 的任务目录里。
- E1 到 E4 的结果（2026-11-25，测到的，同一台机器）。E1：在 E0 的宿主上，Kata 4.2.0 配 QEMU、Dragonball、Cloud Hypervisor 都起得了沙箱，guest 内核用 PVM 项目的 6.12.33；各十次创建、执行、删除全部成功。这回答了上一条留下的问题：PVM 在这款 AMD CPU 上跑得起 guest。创建一个沙箱 6.5 到 8 秒，其中有一段约 5 秒、原因不明的固定间隔；QEMU 的删除偶尔收尾不干净。只测到 containerd 这一层。E2：CubeSandbox v0.8.0 装在同一个宿主上，建模板时 microVM 一启动就复位；用别的 VMM 直接启动它的 guest 内核也一样。E3：换上 CubeSandbox 自己的 PVM 宿主内核之后，它建模板、从模板建沙箱、执行代码都成功，十次全部通过，创建 79 到 99 毫秒。E4：补的对照，用两个 VMM 直接启动 guest 内核。在 Ubuntu 的宿主上关掉五级页表，结果不变；启动参数相同、只换成 CubeSandbox 的宿主内核，两个 guest 内核的结果正好对调。在 CubeSandbox 的宿主内核上，Kata 把 guest 内核换成 CubeSandbox 的之后，Dragonball 和 Cloud Hypervisor 起得了沙箱，QEMU 没有起来。由此有两点要带进计划：这台机器上，PVM 项目的宿主配它的 guest 内核、CubeSandbox 的宿主内核配它的 guest 内核，只有这两种原配的组合起得来，所以说“在 PVM 上”要说清是哪一个宿主配哪一个 guest 内核；这不是“两套实现互不兼容”的一般结论，每边只测了一个版本，换掉的是整个宿主内核，原因没有查。这类机器上两种运行时照各自文档的做法要的宿主不同，要并存现在只有一种测过的搭法，证据很薄。负责人 2026-11-25 说明不需要并存，以后同一个节点上也只放一种运行时（D21），所以并存不再是要解决的问题，那种搭法只作记录。这一条的说法改过两次：E2 刚做完时的归因缺对照，记录复核指出之后用 E4 补了；E4 之后的说法又比证据强，再一次复核之后收窄。
- 改用 Kata 之后，开发机多了一层能做的事：Kind 节点里有 containerd，节点适配器可以在上面用 runc 起沙箱，把账本、准入、父 cgroup、容量变更都走一遍。占位 Pod 的原地调整只用到 Kubernetes，也在开发机做。

## 4. 计划的依据

### 4.1 第一版怎样切

负责人的第一版比提案的阶段一窄。提案把“未修改的 E2B SDK 创建沙箱并执行一条命令”定为第一个里程碑，它比负责人说的多出 E2B 监听器、API key 认证和 Router 到节点的数据转发三块，后者还牵出两项没有结论的待决策。所以第一版不含它们。

“发放 microVM”有两种读法：

| 读法 | 含义 | 取舍 |
|---|---|---|
| 经适配器直接发放 | 池就绪之后，一个命令行工具经节点管理接口创建 | 最短，但 AgentCube 的控制面没有参与，身份与可观测的大部分接缝也不在这条路径上 |
| 经 AgentCube 原生创建接口发放 | 请求经 WorkloadManager 的 `pool` 后端和沙箱调度器 | 多出后端重构、会话存储和调度器，但它才是 AgentCube 发放了一个 microVM，接缝也在这条路径上 |

计划取第二种作为第一版的准出（D3），把第一种作为中间的检查点（里程碑 B）。理由是负责人特别要求保留身份与可观测的可扩展性，而 52 条接缝里约六成（其中身份 26 条里的 18 条）落在会话记录、会话接口和后端分叉之前的调用点上。

2026-11-24 的方向更新改了第一版的两处边界：

- **加进来的：占位 Pod 的手工原地调整**（V1-8，000-12）。提案把它放在阶段二，和自动调节在一起。把手工的部分提前是可行的，因为次序、闸门、操作号这些机制与“谁来决定目标”无关；自动调节以后只是换一个写期望容量的人。
- **拿出去的：一切依赖快照的能力。** 暂停恢复、流量唤醒、模板快速启动原本就不在第一版，现在连“第四版由首个运行时提供”这个前提也没有了，改为第四版之前接入一种带快照的运行时。

### 4.2 首个运行时与几条路线

路线 (a)、(b)、(c) 是第一稿比较的三条；(d) 是 2026-11-24 加进来并被采用的。

| 路线 | 做法 | 代价与未知数 | 结论 |
|---|---|---|---|
| (d) | 首个运行时取 containerd 加 Kata，VMM 由实验定。账本归节点适配器。microVM 在带 KVM 的机器上验证；开发机验 Kubernetes 一侧，并用 runc 当替身验发放路径 | 没有快照、暂停恢复、模板快速启动；账本、准入、开销、网络都要自己做；每次创建是冷启动；仍然要另找一台带 KVM 的机器 | **采用**（负责人 2026-11-24 确认） |
| (a) | 首个运行时取 CubeSandbox，在开发机用 PVM 验证 | 给开发机换内核并重启。单独使用它的节点层时，创建路径上没有找到容量比较；数据入口、事件、到期动作都要另补；sandbox-pool 里对接 kuasar 的部分作废 | 不采用 |
| (b) | 首个运行时取 kuasar-sandbox，microVM 在带 KVM 的机器上验证，开发机只验 Kubernetes 一侧 | 要另找一台机器；容量拒绝是异步的；节点栈的共存形态未定；改容量要重启 conductor | 第一稿采用。现在是带快照的第二种运行时的候选 |
| (c) | kuasar-sandbox 加 PVM 的 guest 内核，在开发机验证 | 路线 (a) 的全部宿主风险；还要重编 guest 内核并修改 kuasar 的代码；没有先例 | 不采用 |

**为什么从 (b) 改为 (d)。** 第一稿选 (b) 有四个理由：接入契约前 9 条在 kuasar 上依据最全；上游自带最短路径的参考实现；负责人指定的参考实现对接的就是它；第一版池大小固定，正好避开它改容量要重启这个短处。范围改为“先走通占位 Pod 的流程，含 resize，不要快照”之后，这些理由的分量变了：

- **第四条反过来了。** resize 进了第一版。kuasar 上每次改容量都要重启 conductor，在途的创建会失败，缩容的下界和回读也有专门的规则。账本归适配器时，改容量是改一个数字和一个 cgroup 的上限。
- **kuasar 的长处用不上。** 它比 Kata 多出来的是快照、暂停恢复、模板快速启动和自带的账本。前三样第一阶段不要；账本是它的，容量拒绝因此是异步的、没有机读原因，这正是第一稿里最大的一条风险。
- **第三条变弱了。** sandbox-pool 对接 kuasar 的代码里，只有“读状态”和“排空”两个调用与 kuasar 当前版本一致，写容量的部分不成立。
- **开发机能验证的更多。** containerd 的接口与运行时无关，可以用 runc 当替身。kuasar 的节点栈在没有 KVM 的机器上能验证到哪一步没有结论。

(d) 的代价也是实在的，写在这里免得以后忘记：

- 以后要暂停恢复和快照时，必须接入第二种运行时，或者等 Kata 上游。节点适配器的接口保持与运行时无关，是这个代价有界的前提。
- 准入的正确性从“运行时保证”变成“我们自己保证”。账本记少了，沙箱的总量就会超出占位 Pod 占住的资源；父 cgroup 是兜底，不是替代。
- 接入契约在 kuasar 上逐条核对过，在 Kata 上没有。契约里与快照、暂停有关的条款 Kata 不满足，第一版如实声明。
- 提案的建议是首个运行时取 kuasar；这里偏离了提案。提案里与 (d) 最接近的是“内置节点栈”：账本归 AgentCube 自己。区别是 (d) 不自己管 VMM，交给 Kata。

**关于在开发机用 PVM。** 开发机是 KVM 之上的 AMD 虚拟机，正是 PVM 面向的那类机器，所以静态上可以尝试。不在开发机做的原因：

- 要换装基于 OpenCloudOS 6.6 的宿主内核并重启。启动参数会改网卡命名并整机禁用 IPv6，重启后可能连不上。
- 这个内核没有 AppArmor 和 KASLR，启动参数关闭 KPTI。Ubuntu 默认靠 AppArmor 约束 Docker 容器。
- 开发机装着只为 6.8 内核构建的 NVIDIA 驱动，换内核后能否重建没有验证；开发机上还有别的工作在用。
- 嵌套 AMD 的 PVM 主机上，CubeSandbox 的候选版本曾经每次创建都失败，后来修复；修复之后在这款 CPU 上是否稳定没有记录。（2026-11-25 补：000-5 的 E3 在一台 AMD 的云主机上、CubeSandbox 自己的宿主内核上，v0.8.0 建模板和十一次从模板建沙箱都成功。只有这一次，谈不上稳定性。）
- 做成了也只证明这类机器能跑 PVM 下的 microVM，不证明占位 Pod 加节点适配器能在 CubeSandbox 上走通。

所以它被放进 000-5，作为可选的对冲实验，在另一台同规格、可丢弃的虚拟机上做。改用 Kata 之后，对冲的内容从“CubeSandbox 加 PVM”换成“Kata 加 PVM”。PVM 项目测试的就是 Kata 配 QEMU、Dragonball、Cloud Hypervisor，依据见第 3.3 节。上面不在开发机做的理由里，前三条照旧成立；用 PVM 项目的模块包可以不换整个内核，但开发机的内核版本没有对应的包，仍然要换内核并重启。

**会改变这个选择的条件。**

| 条件 | 选择变成 |
|---|---|
| 拿不到带 KVM 的机器，而“Kata 加 PVM”的对冲实验通过 | 路线不变，Kata 的验证改在 PVM 的宿主上做。这样的证据能不能作为第一版的准出，由负责人定 |
| “Kata 加 PVM”的实验不通过 | 先分清原因。PVM 的宿主本身起不来：换哪个运行时都一样，只能找带 KVM 的机器。宿主起得来而 Kata 不行：用 CubeSandbox 做对照之后评估 kuasar。kuasar 没有 PVM 的支持，要重编 guest 内核并改代码，不是现成的退路 |
| Kubernetes 之外的容器在 kubelet 的 containerd 上活不住，另起一个 containerd 也不行 | 报给负责人。候选是回到路线 (b) |
| 三种 VMM 都不满足要求 | 改用 QEMU，仍在路线 (d) 之内 |
| 第一阶段的范围加回快照或暂停恢复 | 回到路线 (b)，或者在 Kata 之外接入第二种运行时 |
| 负责人确认首期必须支持没有 KVM 的云主机 | Kata 要靠 PVM 才能满足。先做“Kata 加 PVM”的实验，VMM 不选 Firecracker；不通过时按上一行处理 |

### 4.3 子任务怎样拆

拆分遵循四条规则：

1. **每个子任务能单独验证。** 所以容量交接先接假运行时（000-3），后端接口的重构先于 `pool` 后端（000-8 先于 000-10）。
2. **改行为的与不改行为的分开。** 000-1、000-7、000-8、000-9 都不改变现有对外行为，可以用现有端到端测试当护栏；新行为集中在 000-10，并由开关控制。
3. **与运行时有关的集中在两处。** 000-5 做实验，000-6 里 containerd 加 Kata 的驱动承载全部运行时专有的代码。其余子任务不认识运行时。账本与准入也在 000-6，但它们与运行时无关，换运行时的时候不用动。
4. **定义先于实现。** 000-1 把共用的类型、接口和键名定下来，避免各子任务各写各的。身份与可观测的接缝也在这里统一定义。
5. **resize 单独成一个子任务（000-12），不并进 000-3。** 000-3 证明的是“首次应用容量”这一条最短的链路，先让池能 Ready。resize 的状态机、回退、围栏比它复杂得多，并且提案的两组实验（KE-P3、KE-S6）要先做。它的 Kubernetes 一侧只依赖 000-3 的假运行时，可以在开发机完成，不等运行时的实验。

提案规定的四条先后约束都落在依赖关系里：会话记录的后端字段和后端接口先于第一个池会话（000-7、000-8 先于 000-10）；分配闸门先于首次应用容量（在 000-3 内）；适配器先写操作意图再调运行时（在 000-6 内）；WorkloadManager 先写占位记录再放置，后端确认之后才删记录（在 000-10 内）。resize 的两条次序在 000-12 内：扩容先写 `/resize`、kubelet 分配之后才向节点应用；缩容先向节点应用、成功之后才写 `/resize`。

### 4.4 版本怎样排

- 第二版先做数据面和 E2B，是因为它正是提案的第一个里程碑，也是租户能真正使用沙箱的前提。
- 第三版的加固项互相独立，可以按风险排序，不必一起交付。
- 第四版对应提案的阶段二，提案自己指出它最重。其中自动调节建在第一版的手工调整之上；暂停与恢复要等接入一种带快照的运行时，这一项的取证提前到第二版的时间里做。

## 7. 没有验证的内容

- 除了 000-5 的 PVM 实验，没有执行任何实验。提案的 65 个实验，和本计划在 000-5 里新增的 17 个，都没有做。PVM 的实验原先计划 2 个（E0、E1），实际做了 5 个：E2、E3 是负责人要求验证 CubeSandbox 之后加的，E4 是记录复核之后补的对照。
- Kata 的全部运行行为。Kata 研究笔记是静态阅读。下面四点是计划所依赖的分析，都由 000-5 验证：
  - 不经 CRI、直接经 containerd 的原生接口使用 Kata，包括虚拟机的规格怎样由 OCI 规格决定；
  - kubelet 的 containerd 上，独立 namespace 里的容器不受 kubelet 干扰；
  - runc 可以当 Kata 的替身，即两者在适配器看来只差一个运行时的名字；
  - 池级的父 cgroup 在 Kata 之下兜得住，VMM 和 shim 的进程也在它下面。
- 原地调整在占位 Pod 上的行为。提案的 KE-P3、KE-S6、KE-S8 都没有做，而它现在在第一版的关键路径上。
- PVM 的五个实验各做过一次，都在同一台 AMD 的云主机上。它们只到 containerd 或 CubeSandbox 自己的接口这一层：没有经过 Kubernetes，没有占位 Pod，没有适配器，没有并发，没有长时间运行。
- Kata 在 PVM 上能运行，依据是 PVM 项目的指南、测试脚本和发布说明，计划作者读过，没有运行。E1 在一台 AMD 的虚拟机上验证了 Kata 4.2.0 配 PVM 项目的 guest 内核起得了沙箱，宿主内核是 `6.8.0-139`；开发机的内核版本（`6.8.0-149`）没有对应的模块包，没有验证。Kata 4.4.0 没有验证。
- kuasar 在 PVM 上不能直接用，依据是检索不到和静态的差距分析，同样没有运行。
- kuasar-sandbox 的全部运行行为，包括容量拒绝的形态、带着运行中的沙箱重启 conductor、没有 KVM 时各服务能否启动。它不再在第一版的路径上。
- 档 1 的空操作 shim 是否成立。提案里它的全部应答约定都标为“分析，未实验”，有证据的脚手架是 Rust 的库，Go 的 shim 库只有 sandbox-pool 这一个先例。
- controller-runtime 当前版本在 agent-sandbox 的 CRD 缺失时的确切行为。
- 子任务的规模是相对判断，没有估工期。
- connector 配 Kata。connector 的文档里列的使用方是经 TAP 描述符接入的 VMM，没有 Kata；“veth 端口加 Kata”是计划作者按两边的文档和代码推出来的，没有人验证过。Kind 节点里能不能加载它的 eBPF 程序、guest 里的地址和路由怎样对齐、端口回收再用时 Kata 留在 veth 上的 qdisc 会不会挡住下一次接入，也都没有验证。由 000-5 的 KA-7、KB-7 确认。
- 讨论材料里三种形态的比较。它全部来自静态阅读。agent-sandbox、Kata、CubeSandbox 的数字是各自文档的自述，没有复现，测试条件互不相同，不能直接横向比较。开源的 Kuasar 只读过 README，没有在形态 B 的位置上评估过。CubeSandbox 只用节点层能不能端到端运行没有验证。
- sandbox-pool 的任何运行行为：占位 Pod 能否 Ready、shim 在 containerd 重启后的表现、agent 重启后占位 Pod 是否重建。移植来的代码同样要过子任务的验收，不能因为“原来就有”而免验。
